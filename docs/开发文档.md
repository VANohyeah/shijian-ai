## 1. 一句话定位

用户注册时填一次身体数据，之后**拍菜单**或**选城市**，系统告诉他「这道菜我能不能吃、为什么」。

## 2. 技术选型与理由

| 层 | 选型 | 为什么选它 | 被否决的方案 |
|---|---|---|---|
| 前端框架 | Nuxt 3（Vue 3 + TS） | 团队有 Vue3 基础，10 天不需要学新框架 | Next.js（比赛推荐栈，但需现学 React） |
| 后端 | Nuxt server routes（Nitro） | 与前端同仓同进程，省掉独立服务；比赛允许「后端仅作 AI 接入层」 | Spring Boot（重，且要单独部署） |
| 模型 | 智谱 GLM（主）/ DeepSeek（备） | 国内直连、一个 Key 同时覆盖文本与视觉 | 只用海外模型（网络不可控） |
| 检索 | SQLite + FTS5 | 无外部依赖；DeepSeek 无 embedding 接口，引入向量库要多养一个服务 | pgvector / Chroma |
| 部署 | 单机 + Nginx | 评审期间只需活着 | 容器编排（过度设计） |

```

  │ ② POST /api/dish/analyze  { imageBase64, mime }
  ▼

  │ ③ 校验入参（空值、8MB 上限）
  │ ④ providerChain() 决定用 GLM 还是 DeepSeek
  │ ⑤ 组装 prompt（结构化输出约束）
  │ ⑥ 逐个尝试：模型候选 × 图片传法（dataURI / 裸 base64）
  ▼
智谱 / DeepSeek（OpenAI 兼容）
  │ ⑦ 返回 JSON 文本
  ▼
server route
  │ ⑧ extractJson() 容错解析（去 ```json、截首尾花括号）
  │ ⑨ normalizeDishes() 归一化：空串→null、allergens 白名单过滤、食材中英对齐

## 5. 三条设计原则

1. **Key 永不出服务端**：浏览器只调 `/api/*`，`Authorization` 在服务端拼。
2. **失败要能降级**：模型名、图片格式、供应商三层都有候选，任一成功即返回。
3. **不可靠的东西要标注**：识别结果可人工修正，置信度低的提示核对。

## 1. Dish —— 菜品对象

拍照识别结果与地域菜品库**共用同一个结构**，这是整个方案省时间的关键：健康评估逻辑只写一遍。

```ts
export interface Dish {
  id: string
  name: string                    // 原文菜名，照抄
  name_zh: string | null          // 中文译名；原文是中文时等于 name
  region: string | null
  city: string | null
  ingredients: string[]           // 原文食材，最多 6
  ingredients_zh: string[]        // 中文食材，与 ingredients 一一对应
  method: string | null           // 做法
  flavors: string[]
  spicy_level: 0 | 1 | 2 | 3 | null
  allergens: Allergen[]
  tags: string[]                  // 含系列名，如 ["至尊系列"]
  reference_price: number | null
  source: 'photo' | 'library'
  confidence: number              // 0-1
}
```

### 字段规则

| 字段 | 规则 | 原因 |
|---|---|---|
| `allergens` | 只能取 **12 类**（含麸质谷物/甲壳类/鱼类/蛋类/花生/大豆/乳制品/坚果/贝类·软体/芝麻/酒精/亚硫酸盐），其余一律丢弃 | 白名单 = C 的 `03_禁忌库/allergens.json`，模型可能返回「辣」这类非过敏原词 |
| `name_zh` | 原文含中文时兜底等于 `name` | 中文菜单不重复翻译 |
| `ingredients_zh` | 长度不超过 `ingredients`，超出截断 | 防止前端错位 |
| `reference_price` | 系列价格下发到每个口味 | 中文菜单价格常写在标题行 |
| `confidence` | 0-1；< 0.5 前端必须提示核对 | 识别错食材会给错误健康结论 |
| 空值 | **一律 `null`，不用 `""`** | 空串会让前端出现 `region: ""` |

## 2. UserProfile —— 用户身体档案

```ts
export interface UserProfile {
  gender: 'male' | 'female'
  age: number
  height_cm: number
  weight_kg: number
  activity: 'sedentary' | 'light' | 'moderate' | 'active'
  goal: 'fat_loss' | 'muscle_gain' | 'sugar_control' | 'none'
  allergens: Allergen[]
  conditions: Condition[]      // 痛风 / 高血压 / 糖尿病 / 肾病 / 孕期
  dietary: string[]            // 宗教戒律、素食等
}
```

**BMI / BMR 由前端算好再展示，不塞进模型上下文**——模型只需要结论，不需要公式。

## 3. DishAssessment —— 健康评估结果

```ts
export interface DishAssessment {
  dish_id: string
  level: 'safe' | 'caution' | 'forbidden'
  reasons: string[]     // 如 "含虾皮 → 海鲜过敏"
  citations: string[]   // 如 "八大类过敏原清单"
  suggestion: string | null
}
```

### 判定优先级（写死，不允许模型自由发挥）

```
过敏  >  孕期  >  慢病  >  目标
```

过敏命中一律 `forbidden`，**不允许降级**。这是产品的安全底线，也是答辩时的核心设计点。

## 2. 模型实测（2026-11-09，真实调用）

### 视觉

| 模型 | 结果 | 耗时 | 结论 |
|---|---|---|---|
| `glm-4v-plus-0111` | ✅ 8 道全对，能读懂「系列→口味」层级 | 10–13s | **首选** |
| `glm-4v-flash` | ⚠️ 把分类标题当菜名 | 6–10s | 仅作降级 |

**测试样本**：一张分类式比萨菜单（至尊系列 5 个口味 + 精选系列 3 个口味，价格写在系列标题行）。

- `flash` 输出：`至尊系列 9寸普通庄 / 至尊系列 12寸大庄 / …` —— 全错
- `plus` 输出：`超级至尊 / 海鲜至尊 / 香荤至尊 / 荤素满堂 / 海底金枪 / 榴莲多多 / 夏威夷风情 / 意式培根` —— 全对，价格按系列下发

> **结论：视觉模型准确率优先于速度。** 识别错食材 → 健康结论错 → 产品价值归零。

### 文本

| 模型 | 结果 | 耗时 | 结论 |
|---|---|---|---|
| `glm-4-flash` | ✅ 指令跟随正常 | 0.8–1.1s | **默认** |
| `glm-5.3-flash` | ✅ 更强 | ~3s | 候选 |
| `glm-4.6-flash` | ❌ 403 | — | 本账号未开通，已从候选移除 |

## 3. 降级链设计

```ts
// 供应商层
[GLM, DeepSeek]  ← AI_PROVIDER 可强制指定

// 模型层（同一供应商内按序尝试）
text:   glm-4-flash → glm-5.3-flash
vision: glm-4v-plus-0111 → glm-4v-flash → glm-5.3-flash

// 图片传法（同一模型内按序尝试）
data:image/jpeg;base64,...  →  裸 base64
```

**为什么要三层**：智谱的模型可用性随账号套餐变化，写死一个型号会在某天整体 500。最多试 8 次，全失败才报错，并带出最后一次的原文错误。

## 4. Prompt 设计要点

### 4.1 结构化输出

- system 只留一句：`你是菜单识别器。只输出一个 JSON 对象，不要解释。`
- 所有约束放 user，越具体越好
- **不用** `response_format: json_object`（视觉模型支持度不一），改用「提示词约束 + 代码容错解析」

### 4.2 容错解析（`extractJson`）

模型可能返回：

```
```json
{ "dishes": [...] }
```
```

所以：去 ```json 围栏 → `JSON.parse` → 失败则截取首个 `{` 到末个 `}` 再试一次。

### 4.3 三层结构而非平铺

中文菜单常见「系列标题 → 多口味 + 价格」的排版。若让模型直接输出平铺的菜品列表，它会把标题当菜名。

改为要求输出 `groups[].items[]`，**价格写在组上**，代码里展平下发。这一改动把准确率从 0% 提到 100%（在测试样本上）。

### 4.4 过敏原要「主动推导」

模型默认只从字面找过敏原，结果全空。加入明确规则后：

```
crust/面团/饼底 → 麸质
cheese/奶酪/芝士 → 乳制品
shrimp/蟹/贝 → 海鲜
```

**宁可多报不可漏报** —— 漏报是安全事故，多报只是体验问题。

### 4.5 双语一次生成

同一次调用里同时要 `name`（原文）与 `name_zh`（中文），食材同理。**不要发两次请求**：慢一倍、贵一倍，还可能两套结果对不上。

## 7. 知识检索（RAG 的 R）

- 语料：C 交付的 52 条知识 server/data/knowledge_entries.json，构建期打包
- 实现：server/utils/knowledge.ts，关键词匹配 + 类别加权，纯内存线性扫描
- **不用 SQLite FTS**：52 条语料，一次扫描几十微秒，建表反而多一层部署依赖
- **不用向量检索**：DeepSeek 无 embedding 接口，引入就等于多养一个服务（见决策记录）
- 输出必须带 source，前端展示为「依据」

**触发规则**：只有 level ≠ safe 或带判定理由的菜才附依据。safe 菜附依据会产生噪音（实测过：麻婆豆腐被引到「增肌补蛋白」）。

**实测（成都 + 痛风）**

`
夫妻肺片   caution   常见高嘌呤与中嘌呤食物清单 / 嘌呤含量的三档划分
麻辣兔头   caution   常见高嘌呤与中嘌呤食物清单 / 八大类致敏物质是哪些
开水白菜   caution   常见高嘌呤与中嘌呤食物清单 / 嘌呤含量的三档划分
麻婆豆腐   safe      —
`

**分工**：规则引擎回答「为什么」（可解释、可测试），知识库回答「依据出处」（可溯源）。两者分开，答辩时能分别讲清。

## 1. 启动类

| 现象 | 原因 | 解决 |
|---|---|---|
| `ERR_CONNECTION_REFUSED` | 服务没启动，或窗口被关了 | 在项目目录 `npm run dev`，窗口不能关 |
| 黑窗口一闪而过 | 有报错 | 用 `启动.bat`，或命令行里跑，看完整报错 |
| `EADDRINUSE` | 3000 被占用 | `npm run dev -- --port 3001` |
| 停在 `Are you interested in participating?` | Nuxt 首次启动的匿名统计询问 | 按方向键选 No 回车；或 `npx nuxi telemetry disable` |
| 页面 500 但终端没红字 | 多半是 API Key 没读到 | 打开 `/api/health` 看 `ready` 字段 |

## 2. API Key 类

| 现象 | 原因 |
|---|---|
| `hasKey: false` / `ready: false` | `.env` 没建、名字错了（`.env.txt`）、或改完没重启 |
| HTTP 401 | Key 不对。智谱是 `id.secret` 两段带点的形式，**32 位纯十六进制的是 ID 不是 Key** |
| HTTP 402 / 余额不足 | 账户没钱 |
| HTTP 403 | 该账号没开通这个模型（如 `glm-4.6-flash`） |
| HTTP 404 模型不存在 | 模型名写错，或型号已下线 → 加进候选列表自动降级 |

**关于智谱 Key 的坑**：控制台列表里显示的是遮罩值 `be43...JiR6`，看不到完整值。必须点「新建 API Key」，在弹窗里复制完整的两段式字符串。

## 3. 中文乱码

**现象**：curl / Postman 里返回 `å¹²é"…`，但浏览器正常。

**原因**：响应头只有 `application/json`，没有 `charset=utf-8`，非浏览器客户端按 Latin-1 解码。

**解决**：服务端显式设置

```ts
setResponseHeader(event, 'Content-Type', 'application/json; charset=utf-8')
```

**附带的坑**：PowerShell `Invoke-WebRequest` 发请求时，如果 body 是字符串，会按非 UTF-8 编码发出，中文变成 `??????`，模型会说「你的输入是乱码」。**测试脚本要传字节**：

```powershell
Invoke-WebRequest ... -Body ([Text.Encoding]::UTF8.GetBytes($json)) `
  -ContentType "application/json; charset=utf-8"
```

## 4. 识图类

| 现象 | 原因 | 解决 |
|---|---|---|
| 把「至尊系列」当菜名 | 模型读不懂分组排版 | 换 `glm-4v-plus-0111`；prompt 改成 groups/items 三层 |
| `allergens` 全空 | 模型只找字面词 | prompt 里写明推导规则（饼底→麸质、奶酪→乳制品） |
| `ingredients` 全空 | 没要求推断 | prompt 里给示例：「海鲜至尊 → 虾、蟹、贝类」 |
| 返回带 ```json 围栏 | 模型习惯 | 代码里 `extractJson` 清理，别指望模型每次都听话 |
| 识别超时 / 很慢 | 图片太大 | 客户端压到长边 1280px、JPEG 0.85 |
| 分类标题和口味混在一起 | 平铺 schema 的必然结果 | 用 groups 结构，价格挂在组上 |

| 现象 | 原因 |
