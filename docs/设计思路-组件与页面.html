项目速读：三句话讲清食鉴

用户填一次身体档案（性别、年龄、身高体重、过敏原、慢病、孕期、减脂目标），之后无论是 拍一张菜单还是挑一座城市，系统逐道回答：「这道菜我能不能吃、为什么、依据是什么」。

它和大众点评、美团不是同一类产品。那些平台解决「去哪吃」，食鉴解决「你能不能吃」—— 一个过敏体质的孕妇站在一桌菜前面，没有人替她把这句话说出来，这就是缺口。

要记住的事内容对界面的直接影响
判定不在模型手里 evaluateRules(dish, profile) 是纯函数，等级靠 raise() 只升不降（safe 0 < caution 1 < forbidden 2），最终取所有命中项里最高的那个。
能把一道菜判成 forbidden 的只有四种来源：过敏、孕期生食、素食、清真；慢病与减脂目标最高只到 caution。		 结论必须由界面盖章式给出，不能是「AI 觉得」的软话；理由与依据要和结论分开摆。
也别把「高血压」画成红色炸弹——按引擎它只够「注意」。
模型只干两件事 ① 读图认菜：vision 模型抽菜名、食材、置信度，temperature: 0，多 provider × 多模型 × 多图变体最多试 8 次；② 把结论写成人话。
它不参与判定，也改不了等级。		 界面上凡是「模型可能错」的地方都要留后路：低置信标注、菜名可改、食材可删补。
凡是「规则算出来的」地方不给改：结论、依据。
数据底数 30 座城市、250 道菜（250 / 250 都带 reference_price）、310 条知识、12 类过敏原。 有价就显示 ¥，没有就不摆占位框；空字段一律不占行。
只有三档结论 safe / caution / forbidden，对应三色：Forest / Olive / Brick。 三色必须一眼可分，且不能只靠颜色——色盲用户与黑白打印都要能读。
识别一定会有错 菜品可改：菜名用 input 直改，食材用可删 chip 补录（决策 F6）。 「可修正」是主交互，不是兜底按钮：改完的结论就地重算。
视觉已定调 复古怀旧：#f5e6d3 泛黄纸、#8b4513 棕褐、圆角 4px、边框 2px、无阴影、过渡 300ms。 所有新组件必须在这套约束里生长，不许冒出玻璃态、大圆角、现代渐变。
八个路由、四条线 / 分流 → 现场线 /scan；闲逛线 /cities → /city/[id] → /dish/[id]；个人线 /profile、/favorites、/chat。 复用率必须高——八个路由撑不起一套冗余组件库；排列与跳转见第伍章页面地图。

外部经验：被验证过的四件事

做美食界面不是从零发明。下面四条是查证过的行业结论，后面每个组件的规格都能追到其中一条。

一、组件要分层，别按页面切

美团技术团队复盘外卖近百个页面后，把组件按粒度分成四层：基础控件（标签、按钮、开关）→ 业务组件（商品卡片）→ 复杂组件（多个业务组件拼合）→ 模板（商家列表、菜品列表）→ 页面。他们的结论是：先按「使用频率」排序再逐个替换，否则组件库做得很全，实际一大半用不上。

复用性较高的组件大体可分为两类：第一类是「基础控件」……第二类是「业务组件」，由基础控件组成， 同时业务组件还能相互组合，成为更高阶的「复杂组件」。 美团技术团队《移动端 UI 一致性解决方案》，2020-11-26

这条直接决定了本文档第叁章的组织方式：不按页面列组件，按粒度分层。八个路由共用一套组件， 比八个路由各写一套划算得多。

二、菜品卡只有半秒，顺序不能乱

食物类产品卡片的元素有固定的注意力顺序：图片 → 名称 → 价格 → 评分/徽章 → 可定制信号。 拇指滑过一张卡的时间大致就是半秒，价格和图片要先于评分被识别，评分又要先于徽章。 另有研究显示菜单单品加照片后销量平均提升 6.5%（Cornell 菜单研究），外卖平台则给商家开出「加图能提升 30% 以上订单」的建议。

A product card has about half a second to make its case before someone's thumb scrolls past it. Design Your Way《Food App Design: Half a Second to Make the Sale》

食鉴有参考价（seed/dishes.json 里 250 道菜全部带 reference_price， scan.vue 已渲染 .dish-price），没有评分。那半秒要争夺的东西因此变成： 结论 → 菜名 → 参考价 → 理由。判定必须顶在菜名同一行，而不是藏在卡片底部； 价格用衬线 17 落在菜名右侧，读到就停，不用横扫。

三、过敏原信息「只靠颜色」是安全缺陷

这是本项目最不能妥协的一条。把饮食禁忌编码成小色点，在 WCAG 里同时踩两处： 1.4.1 不只用颜色 与 1.1.1 非文本内容需有替代文本。约 8% 的男性存在不同程度的色觉障碍， 红绿色盲最常见；对严重过敏的用户，这不是审美问题，是安全问题。行业给出的做法一致：

要做的具体做法
颜色 + 文字 + 形状，三重编码每个标记都带文字（「含虾」）或 aria-label（"Contains shellfish"）；色块只是加速识别，不能是唯一线索。
灰阶自测把界面截图转成灰度，如果信息变得含糊或消失，说明存在颜色依赖。
明度也要拉开即使色相看不出，深绿与浅橙的明度差也能区分；三色不要选明度相近的。
触控目标 ≥ 44×44手机上的筛选项、可删 chip 的关闭按钮都要留足手指面积（视觉可以做小，命中区不行）。
对比度 ≥ 4.5:1标签文字与底色之间，三个状态都要达标（含选中态）。

四、AI 的不确定性要设计出来，而不是藏起来

模型输出是概率性的，界面若用同一种「确定的字体」渲染所有结果，用户会学会不信任全部结果。可用的四条做法：

别甩裸数字

「置信度 0.72」对人没有意义。换成能判断的说法：「照片偏暗，两道菜名需核对」。

按风险分档呈现

低风险高置信 → 直接给结论；高风险低置信 → 放进「待核对」，要求人确认后才生效。

改比重来便宜

输入要留在输出旁边：能在原处改一个字，就不要让人重新拍一张。部分结果应可保留。

等待要变成证据

转圈只消耗时间。分步播报「正在读菜单 → 识别到 8 道 → 正在比对禁忌」会把等待变成可信度。

Confidence is a design decision, not a number. … The failure mode to avoid is a product that renders every output with the same typographic certainty. Farba Digital《Designing for the AI that gets it wrong》

一共八个路由、四条线。这张表不是设想，是 pages/ 目录现在的样子（2026-11-13 逐文件对过）。 拍菜单和挑城市是两条平行的腿，谁都不依赖谁；档案、收藏、对话挂在个人线上。

另外 /login、/register 不做，deviceId 暂代账号；/plan 已做进 plan.post.ts，未单开页面。

二、四条线怎么排

  1. L0入口 / — 只做分流，不承载内容
    1. L1现场线 /scan — 站着用：拍完就地出结论
      1. L2结果 就地展开 — 不跳页，详情能力内联在卡里
    2. L1闲逛线 /cities — 坐着用：慢慢挑
      1. L2一座城 /city/[id] — 这座城的清单
      2. L2一道菜 /dish/[id] — 深页
    3. L1个人线 /profile /favorites /chat — 顶栏三处，互不串联
为什么这么放理由
/ 只做分流首页不塞推荐流、不塞榜单。它的全部工作是让人在两秒内决定「拍一张」还是「挑座城」；多一块内容就多一个分心点。
两条臂并列，互不依赖拍菜单不需要先选城市，选城市也不需要先拍照。两个入口平权，用户从哪个场景进来都能走到底。
档案挂顶栏而不是挡在门口现状如此，但代价要认：不填档案就用默认值算，结论会错。补 middleware 是当前第一优先项。

三、为什么拍完菜单不跳详情页

这是整套路由里唯一一个「反直觉」的决定：/scan 出了结论，不跳 /dish/[id]。

因为使用场景不一样。拍菜单是站着用的：人站在餐厅里，举着手机，刚拍完一张，眼前是一桌菜和一位服务员。 这时候跳页意味着丢掉那张照片、丢掉整桌菜的上下文，想再看第二道菜得退回重来。 所以 scan 的结论必须就地展开——菜名可改、食材可补、理由和依据都写在卡里，改完立刻重算。

挑城市是坐着用的：人在家、在办公室，愿意点进去看一道菜的来龙去脉。这种场景才配一个独立详情页，装得下理由、依据、替代建议三段。 一句话：越是现场，越不能跳页；越是闲逛，越可以深进去。

五、三条跳转原则

守卫收口，页面不收口

判档案只在一个全局 middleware 里做。八个路由各自判，迟早漏一个——漏了就是用默认档案算出一堆错结论。

就地优先，跳页要付代价

同一屏能解决的不跳。非跳不可，回来要能恢复现场：照片还在、滚动位置还在、改过的菜名还在。

返回必须有兜底

分享链接直接打开时历史是空的，router.back() 会把人退出站点。每个返回都要有确定的一页接住。

六、现在有五个缺口

拿这张地图去对了一遍代码（2026-11-13），五处对不上。前两条影响走查，后三条影响验收与合规。

#缺口具体表现怎么补
1 没有档案守卫 没有 middleware/ 目录。用户不填档案也能直接进 /scan、/city/[id]，判定会退回默认档案（女 / 25 / 165 / 55 / 无过敏原）。 补 middleware/onboarding.global.ts：无档案跳 /profile，接口异常放行。
2 /scan 没有回首页的入口 页头只有标题，拍完只能靠浏览器后退；移动端从相机回来最容易迷路。 补一个「← 返回」，落在 /。
3 /dish/[id] 的返回没兜底 只有 router.back()。分享链接直接打开时历史为空，按下去会退出站点。 判断 history.length > 1，否则落到 /cities。
4 「最近看过」不可点 index.vue 里是 div.mini + strong，没有链接，标题和日期都是死的。 历史记录里存了 dishes，要么补跳转，要么把标题改成「记录」不暗示可点。
5 免责声明只有 /chat 有 其余七个页面都没有「不构成医疗建议」。这是 AI 安全评分项的明面要求。 统一页脚组件，一句话：「判断依据是你填的档案和公开的食材禁忌资料，不构成医疗建议。」

说明：第 1 条不是「文档写得比代码好」，而是代码确实缺一块。文档先写清目标，代码随后补上——比反过来强。

七、以后加页面，先过两道关

第一关：它是第几层。 L0 和 L1 各只许有一个。想再加一个「首页级别」的页面，先问是不是首页没想清楚。 L2 是入口（拍 / 挑），L3 是结果与详情——新页面要么是新的臂，要么是新的层，不能模棱两可。

第二关：深链能不能直达。 /city/beijing 复制出去，别人打开要能直接看到那座城。 现在守卫跑在客户端（import.meta.server 时直接返回），冷启动会先渲染一帧再判断， 可接受，但要知道有这一帧——做加载骨架时别让它闪出首页内容。

陆

设计思路：为什么这套皮相配这道菜

美食类界面最容易滑向两种默认：暖橙色的外卖流，或奶油底 + 大衬线的「生活方式」风。前者在催你下单， 后者在卖氛围。食鉴两样都不是——它是一张被人反复核对过的纸：点菜之前，先看一眼有没有踩雷。 复古怀旧刚好长在这个动作上。

三条根：设计不是从审美开始的

约束它决定了什么
它是工具，不是内容站 用户只在餐厅坐下时打开它，三十秒内要答案。所以一屏扫完，不做滚动叙事，不在首屏讲品牌故事。
判定是硬的，视觉就得硬 结论只有三档、由 server/utils/rules.ts 的纯函数算出，不经过模型发挥。界面要是用软话、用弹窗说「AI 认为可能……」，等于把硬结论又还给了猜测。所以：盖章、粗描边、无圆角、无阴影。
10 天、3 个人 组件每多一套，联调就多一处错。所以同类信息共用一个组件：DishCard（识别 / 城市 / 收藏三处共用）、VerdictBadge（三色判定）、ProfileForm（档案三屏）。

四条从产品长出来的映射

产品的真实动作视觉对应为什么成立
对着菜单逐道核对 纸张质感、印刷字体、2px 细边框、虚线分隔 用户本来就在看一张纸（纸质菜单、菜单照片）。界面接管的是同一张纸，认知不用切换。
给出「能不能吃」的结论 邮戳标签 + 判定灯，像给菜单盖一个章 盖章是「已经核对过」的动作隐喻；比弹窗、比彩色胶囊更符合「结论」这件事的分量。
规则引擎当场算出三档 三色只取 Forest / Olive / Brick，不用现代红绿 印刷油墨的红绿比屏幕红绿更沉，既有警示力又不刺眼；同时避开「红灯停绿灯行」的廉价感。
识别需要 5–15 秒 过渡统一 300ms、不位移、不缩放；旧纸不浮动 这套动效观本身就是「慢而不慌」的承诺——慢是可以的，但每一步都要有交代。

纸的四条物理规则

  1. 01旧纸张不会浮起 — 没有阴影、没有 hover 位移、没有 scale，一切平贴在桌面上
  2. 02纸会氧化，但很慢 — 过渡 300ms，最短不低于 150ms；快过这个数就像塑料
  3. 03纸没有大圆角 — 圆角 4px，边框 2px 起；圆角越大越像塑料卡片
  4. 04纸只靠线条和留白分层 — 不用渐变做层次，靠 1px 虚线、2px 实线、以及空白

判定怎么落：两层编码

判定灯：9px 小标记，颜色 + 形状 + 文字三重编码——可以吃＝实心圆（Forest）、注意＝方块（Olive）、别点＝菱形（Brick）。 三态固定，不可新增第四态；灰阶下靠形状仍可分。这正对应第二章那条外部经验：过敏原信息只靠颜色，是安全缺陷。

徽章用方戳（4px 圆角）而不是胶囊：胶囊里再塞形状标记会糊。三色仍是森林绿 / 橄榄 / 砖红，不用现代红绿——那是交通灯，不是食物。

克制点：只在一处用力

整套界面只允许一个地方「使劲」——判定结果。菜名是衬线 900，理由是无衬线常规，页面其余部分一律安静： 没有插画、没有渐变、没有装饰性图标、没有 hover 位移。评委记住的应该是「这菜我不能吃」， 而不是「这个页面动效真花」。

四条禁令 不做 transform: scale() / translateY()；不做渐变与玻璃态；不做大圆角（一律 4px）；过渡不短于 150ms、组件统一 300ms ease-out。

文案七条

规矩例子
结论与依据分开摆结论用盖章口吻（「别点」），依据写清出处（「八大类过敏原清单」）。不许混成「本品可能不适合您」。
按钮写动作「开始识别」不是「提交」，「保存档案」不是「确定」。
标题直接说内容「同样一桌菜，答案因人而异」，不是「欢迎使用食鉴」。
人称统一对用户称「你」，产品自称「食鉴」。
空列表给下一步「还没有记录。先去填一份档案，再去拍一张菜单。」
无依据时明说「不确定，建议问店员」——禁止生成听起来合理的推测。
不出现「治疗」「预防疾病」「根治」。

颜色、字体、圆角、间距的数字见文末附章「视觉规格速查」（六档字号、一套色板）；本章只讲「为什么」。 字体是打包的思源宋体可变子集（public/fonts/han.woff2，719 KB，200–900 字重轴）， 不用系统宋体——Windows 自带宋体没有 900 字重，浏览器会伪粗描边，大字糊成一团。

捌

三条红线与六项自检

一 · 判定归代码

过敏一命中就是 forbidden，界面不许出现「建议少吃」这类软化。模型只写解释，不改结论。三档不许新增第四档。

二 · 不能只靠颜色

每个判定都要颜色 + 形状 + 文字三重编码；提交前把界面转灰度看一遍；标签对比度 ≥ 4.5:1；触控目标 ≥ 44×44。

三 · 不编造、不越界

知识条目必须有来源；没把握就说「建议询问店员」。任何界面不出现「治疗」「预防疾病」；页脚固定免责声明。

交付前的六项自检

#检查项合格标准
1灰阶可读整页截图转灰度，三档结论仍能分辨——这一条现在过不了，见台账体检第 1 条。
2键盘可达Tab 能走完主流程，焦点始终可见（2px 棕描边 + 3px 偏移）。
3移动端 390px单列不横向滚动，主行动按钮在拇指区，删除叉可点中。
4三态齐全每个列表有空态、加载态、错误态；每个可点元素有 hover / active / disabled。
5文案无空话没有「系统繁忙」「请稍后再试」；每个错误都告诉用户下一步做什么。
6无禁忌词全站搜索「治疗」「预防」「根治」，零命中。

别用手点：跑一遍 scripts/verify.ps1

仓库里有现成的端到端校验，四步串起来跑：健康检查 → 上传一张菜单图 → 逐道评估 → 打印三档计数。 交作业前一天跑一次，比在浏览器里手点十遍可靠——它能抓到的正是手点容易漏的那种错（接口活着但规则没命中）。

用法：powershell -File scripts/verify.ps1 -Base http://localhost:3000 -Image test-menu.png。 第二个参数可换任意测试图，不传就用仓库根目录的 test-menu.png。

两个容易被问倒的实现细节

过敏原有双保险

模型报回来的 allergens 不一定全。inferAllergens() 会拿 12 类过敏原的关键词表 在「菜名 + 食材 + 标签」里再扫一遍，与模型结果取并集。

还专门处理了一个坑：鱼香肉丝没有鱼——只有「鱼」这一个证据且来自「鱼香」时，剔除「鱼类」。 这条兜底意味着界面上的判定比模型更稳：模型漏报，规则补上。

等级只升不降

raise() 只比较不覆盖（safe 0 < caution 1 < forbidden 2）， 所以「过敏命中后又被减脂目标算了一遍」不会把结论降回去。

这也是为什么理由可能是多行的：一道菜同时踩过敏与高血压，就两条理由、两条依据，等级取高的那个。 citations 最后还做了一次 new Set() 去重。

玖

收尾顺序：按代价排，不按页面排

六个页面全做完了，「分四批做」那张表已经过期。现在要排的不是「先做哪页」，而是 「哪个洞必须堵、哪个可以带着上答辩」——排序依据换成「改一句 CSS，还是改数据流」。

P0 · 半天内能改完，但直接影响现场演示

改什么为什么是 P0代价
判定徽章补形状 灰阶自检现在过不了；红绿色盲在现场看到的是三个一样的深色胶囊。 一个 ::before，三行 CSS
删掉 .dish-name:focus 里的 outline: none 键盘走到菜名上完全看不出焦点在哪，直接违反自家第 2 条自检。 删一句
删除叉撑到 44×44 手机上按不中，演示时会连续点三次才删掉一个食材。 一个 ::after，inset: -12px
统一空档案的行为 扫描页拿默认档案照算、城市页拒绝判定，同一个产品两套态度。 扫描页去掉 ?? {} 兜底，改成和城市页一样的提示

P1 · 一两天，决定「这个产品讲不讲得通」

改什么为什么
识别进度改成四行5–15 秒的黑箱是演示里最难受的一段。数据本来就有，只是没留下来。
扫描结果加一行「看这道菜 →」/dish/[id] 现在只有城市页能进，扫描链路够不着「说清楚为什么」的那一页。
收藏要么给入口、要么先撤存了没处看，比没有更伤。首页加一段「收藏的菜」成本最低。
首页「最近看过」可点列表点了没反应，等于告诉用户历史不重要；summary 字段也该渲出来。

P2 · 有空再动，动之前先想清楚值不值

改什么为什么排最后
把 .badge / .chip / .error 抽成共用组件收益是「以后改一处」，不是「现在更好看」。评分不看组件化——除非答辩要讲工程性，那就只抽 .badge 一个，十分钟能讲完。
.stamp 用起来或删掉零引用的全局样式是负担，但不影响任何页面。
补「替代菜」建议要动后端（得先知道同城还有哪些 safe 的菜），前端单方面做不了。
城市浏览写进 history类型里有 'city' 却永不产生，属于「别让类型撒谎」的洁癖，不影响演示。

排序原则一句话：先改「不花钱就能改对」的，再改「要多写代码」的，最后改「要动后端」的。 每个 P0 都不超过半天，但每一个都落在评委看得见的地方。

明确不做的四件事（答辩时主动说）

比「做了什么」更能说明你懂取舍的是「知道该不做什么」。下面四条在 docs/decisions-frontend.md 里 记的是「未完成（明确不做）」，不是来不及，是想清楚了不做。评委问起，照这张表答，别临时编理由。

不做的为什么不做
语言视角 / 复刻视角 + /api/dish/explain 需要后端补一个模型接口，属另一个人（A）的目录。时间优先给「档案 → 拍菜单 → 结论」这条主线。
/plan 点菜组合 原方案里本来就排在 P1。它依赖先有可靠的逐道判定，本级还没到那一步。
登录 / 注册 用 deviceId 代账号，演示场景够用。真做登录会多出会话、找回、注销三个页面，收益配不上成本。
MCP server 评分里占 4%，但是独立工程，不影响主流程与界面质量。

最后一句：这份文档的地位

它是说明书，不是设计稿。写页面前查它，改规格后回写它。真正的真源只有两处： 视觉看文末附章，判定看 server/utils/rules.ts。 本文件里凡是与这两处冲突的地方，以那两处为准，并且回来改本文件——别让第三份真源长出来。

附

视觉规格速查：所有数字都在这一页

前面几章讲「为什么」。这一章是「具体多少」——颜色、字号、圆角、间距、组件样式。 改样式之前先在这里查数，别凭感觉填。

一句话

旧纸张不会浮起——一切安静地待着，只有颜色在缓慢氧化。

技术约定

  • 项目没有 Tailwind，样式手写：全局在 assets/css/main.css，页面内用 scoped style。
  • 字体不引外部 CDN（中国大陆加载不稳），用系统回退栈。
  • 圆角一律 4px，邮戳标签也不例外（不做胶囊）；边框 2px 起；没有阴影。
  • 过渡一律 var(--dur) var(--ease)（300ms），最短不低于 150ms。
  • 禁止 transform: scale()、translateY()、渐变、玻璃态（backdrop-filter）、霓虹色、大圆角。
  • 标题只用打包的 Han Serif 子集，不许引系统里的 Noto Serif SC——评委机器上没装，会退回宋体并伪粗。新增文案后重跑 python scripts/subset-font.py。

字体

标题用打包的思源宋体可变子集：public/fonts/han.woff2（约 700 KB，约 1900 字）， CSS 名 Han Serif，字重轴 200–900。 为什么打包：评委机器上没装 Noto Serif SC，CSS 会回退到宋体并伪粗描边，大字糊成一团。 为什么用可变版：单一 900 撑不起大刊头——60px 的 900 重得像块砖，400 才有旧书题签的轻。 无衬线栈：Inter, -apple-system, 'Microsoft YaHei', sans-serif。

布局

  • 最大宽度 1120px，容器内边距 32px；区块间距 96px（移动端 48px）
  • 卡片内边距 32px，元素间距 24px，基础单位 8px
  • 移动端（< 768px）：单列，容器内边距 20px，卡片内边距 20px
  • 最小字号 12px

首页规矩

首页是全站唯一的叙事页：可以有摄影、可以铺满屏幕、可以留大片空。但材质规矩一条都不放宽。

  • 首屏：全幅照片 + 居中叠字。遮罩只用单色 rgba(61,36,16,.34)，不用渐变；底图先在 public/hero-table.jpg 里压暗，靠图本身变暗，不靠 CSS 叠层。原图留在 assets/pictures/。
  • 导航：默认浅色字（压在照片上），滚过 120px 转不透明奶油底、深色字。不用 backdrop-filter。
  • 悬停：只改边框色。不位移、不缩放、不加阴影。
  • 删掉的装饰：全大写英文小标签、卡片上的壹贰叁编号、英文菜名行、三栏数字下的拉丁文。删掉它们，信息一点不少。

内容密度

入口卡不许做成「高盒子 + 三行字」。每张卡必须带一块真实内容的示意区：

  • 拍菜单 → 菜单缩略图 + 三条识别结果（带三色圆点）
  • 选城市 → 三座城市 + 各自的代表菜

理由：空盒子像没做完，评委一眼看不出产品在干什么。示意内容要用 seed/ 里真实存在的地名和菜名。

文案

  • 按钮写动作：「开始识别」「保存档案」，不写「提交」
  • 标题直接说内容，不写「欢迎来到……」
  • 空列表给一句说明 + 下一步
  • 任何地方不出现「治疗」「预防疾病」
  • 身体设置那一页统一叫 「你的情况」。不叫「身体档案」（太僵硬，像体检单），也不叫「忌口」（名不副实——第一步填的是身高体重）

状态

  • 每个可点元素必须有：hover / active / disabled / loading
  • 列表必须有：空态 / 加载态 / 出错态
  • 判定结果必须三色区分，forbidden 不许和 caution 长得像

怎么用这份文档

加页面前：先翻第伍章页面地图，答出「它是第几层、从哪进、返回落到哪」；写界面前：翻第叁章找现成组件，别新造； 定样式前：翻第肆章样张核对数值；交付前：过第捌章六项自检， 并重跑一遍第叁章末尾的台账体检。改任何一处规格，只改本文件附章这一处，别让规格散落在代码里。

判断依据是你填的档案和公开的食材禁忌资料，不构成医疗建议。
