## 第一章 项目概述

### 1.1 一句话

用户填一次身体数据，之后无论**拍菜单**还是**选城市**，系统都告诉他「这道菜我能不能吃、为什么」。

### 1.2 要解决的问题

点评类平台解决了「去哪吃」，但没有解决「我能不能吃」：

- 过敏人群在外就餐时，只能靠反复询问店员，且得到的回答往往是「应该没有吧」；
- 痛风、高血压、糖尿病、孕期人群需要判断的不只是「辣不辣」，而是嘌呤、钠、糖、生食与酒精；
- 减脂与控糖人群需要的是「这道菜的油盐水平」，而不是评分与人均价格。

食鉴提供的是**判断依据**，不是推荐列表。

### 1.3 目标用户

| 人群 | 核心诉求 |
|---|---|
| 食物过敏者 | 这道菜里有没有我的过敏原 |
| 慢病人群（痛风 / 高血压 / 糖尿病 / 肾病） | 这道菜能不能吃、能吃多少 |
| 孕期人群 | 有没有生食、酒精、高汞鱼类 |
| 减脂 / 增肌 / 控糖人群 | 油脂与糖的负担 |
| 旅行者 | 到一个陌生城市，哪些本地菜适合我 |

### 1.4 成果概述

| 维度 | 成果 |
|---|---|
| 页面 | 7 个完整页面（首页、拍菜单、城市、城市详情、菜品详情、档案、我的） |
| 接口 | 10 个后端接口 + 1 个 MCP Server（5 个工具） |
| 数据 | 250 道地域菜 / 30 城 / 250 条语言视角 / 25 道复刻菜谱 / 52 条禁忌知识 / 12 类过敏原 |
| 构建 | 2.39 MB，gzip 618 kB |
| 提交 | 13 次提交，跨 5 天，逐日递增 |

## 第二章 需求分析

### 2.1 使用场景

**场景一：在外就餐**

用户落座，拿到纸质菜单。拍照后，系统识别出 8 道菜，逐道标出：海鲜至尊（⛔ 甲壳类过敏）、开水白菜（⚠️ 高汤，痛风需限制）、蒜泥白肉（✅ 可吃）。用户可以据此点菜，也可以点击任意菜品看「怎么点」的话术。

**场景二：去陌生城市**

用户到大阪以外的成都出差，打开「找地方菜」，选成都。系统直接列出 9 道本地特色菜，并按档案标好三色——**不需要拍照，也不需要提问**。

**场景三：在家复刻**

用户想吃某道菜，点进详情页的「复刻视角」，得到备料清单、步骤、以及「过敏怎么换料」。例如麻婆豆腐：郫县豆瓣换成无麸质豆瓣（但大豆过敏者不可用），改用「辣椒酱 + 盐」并加香菇粉补鲜。

### 2.2 功能需求

| 编号 | 功能 | 优先级 | 状态 |
|---|---|---|---|
| F1 | 菜单图片识别为结构化菜品 | P0 | 已完成 |
| F2 | 结合档案给出三色判定与依据 | P0 | 已完成 |
| F3 | 地域特色菜推荐（带判定） | P0 | 已完成 |
| F4 | 身体档案持久化 | P0 | 已完成 |
| F5 | 菜品详情（语言 / 复刻视角） | P1 | 已完成 |
| F6 | 点菜组合（人数 + 预算） | P1 | 已完成 |
| F7 | 收藏与历史 | P1 | 已完成 |
| F8 | MCP 工具暴露 | P2 | 已完成 |
| F9 | 账号体系 | P2 | 不做（见 6.5） |

### 2.3 非功能需求

| 项 | 要求 | 达成情况 |
|---|---|---|
| 识别延迟 | 15 秒内可接受 | 实测 3–13 秒，偶发 30 秒以上（上游模型波动） |
| 判定延迟 | 200 毫秒内 | 实测 22 毫秒 |
| 判定可解释 | 每条结论必须有理由与依据 | 全部带 reasons + citations |
| 密钥安全 | Key 不得出现在前端与仓库 | 仅服务端环境变量，`.env` 已 gitignore |
| 移动端 | 可单手操作 | 响应式布局，针对手机宽度优化 |

## 第三章 系统架构设计

### 3.1 分层结构

```
浏览器（Nuxt 3 / Vue 3 / TypeScript）
  ├─ 7 个页面 + 4 个通用组件
  └─ composables/useProfile：deviceId 与档案读写
        │  HTTP / SSE
        ▼
Nuxt server routes（Nitro，仅作 AI 接入层）
  ├─ 供应商解析：GLM / DeepSeek，模型与图片格式三层降级
  ├─ 规则引擎：纯函数，无模型参与
  ├─ 知识检索：52 条知识，关键词 + 类别加权
  └─ 存储：JSON 文件（收藏 / 历史 / 档案）
        │
        ▼
  智谱 GLM（视觉 + 文本）· Key 只在服务端
```

### 3.2 技术选型与理由

| 层 | 选型 | 理由 | 被否决方案 |
|---|---|---|---|
| 前端 | Nuxt 3 + Vue 3 + TS | 团队有 Vue 基础；几天内不需要学新框架 | Next.js（比赛推荐栈，但需现学 React） |
| 后端 | Nuxt server routes | 与前端同仓同进程；赛项允许「后端仅作 AI 接入层」 | Spring Boot（重，需单独部署） |
| 模型 | 智谱 GLM 为主，DeepSeek 备用 | 国内直连；一个 Key 同时覆盖文本与视觉 | 纯海外模型（网络不可控） |
| 检索 | 内存关键词检索 | 52 条语料，微秒级；无部署依赖 | 向量库（DeepSeek 无 embedding 接口） |
| 存储 | JSON 文件 | 避免原生模块编译风险；单实例演示足够 | SQLite（better-sqlite3 需编译环境） |
| 身份 | deviceId | 省赛不做账号；接口保持 userId 语义 | JWT 账号体系（工期不够） |

### 3.3 目录结构

```
czb比赛/
├─ app.vue / nuxt.config.ts
├─ assets/css/main.css          全局样式
├─ components/                  AppHeader · DishCard · VerdictBadge · ProfileForm
├─ composables/useProfile.ts    deviceId + 档案读写
├─ pages/                       index · scan · cities · city/[id] · dish/[id] · profile · favorites
├─ server/
│  ├─ api/                      scan · evaluate · plan · profile · cities · dishes · user · chat · health
│  └─ utils/                    ai · rules · retrieve · catalog · content · store
├─ mcp/server.mjs               MCP Server（零依赖 JSON-RPC over stdio）
├─ seed/                        城市 / 菜品 / 知识 / 语言 / 菜谱
├─ shared/types.ts              前后端共用类型（唯一真源）
└─ docs/                        开发文档 · 接口契约 · 决策记录
```

### 3.4 核心数据模型

```ts
interface Dish {
  id: string
  name: string              // 原文菜名
  name_zh: string | null    // 中文译名（外文菜单）
  region: string | null
  city: string | null
  ingredients: string[]
  ingredients_zh: string[]
  method: string | null
  flavors: string[]
  spicy_level: 0 | 1 | 2 | 3 | null
  allergens: Allergen[]     // 12 类，白名单校验
  tags: string[]
  reference_price: number | null
  source: 'photo' | 'library'
  confidence: number
}
```

**设计要点**：拍照识别结果与地域菜库**共用同一个结构**。因此健康判定逻辑只写一遍，两个入口都能用——这是整个方案省时间的关键。

### 3.5 一次识图请求的完整链路

1. 浏览器选图 → canvas 压缩（长边 1280px、JPEG 0.85）
2. `POST /api/scan` → 服务端校验入参（空值、8MB 上限）
3. 供应商链决定用 GLM 还是 DeepSeek
4. 逐个尝试：模型候选 × 图片传法（dataURI / 裸 base64）
5. 模型返回 JSON 文本 → 容错解析（去 ```json 围栏、截取花括号）
6. 归一化：空串转 null、过敏原白名单过滤、中英食材对齐
7. 前端渲染菜品卡片，随后调用 `/api/evaluate` 得到三色

## 第四章 AI 技术方案

### 4.1 模型选型（实测）

**视觉模型**

| 模型 | 结果 | 耗时 | 结论 |
|---|---|---|---|
| `glm-4v-plus-0111` | 8 道全对，能读懂「系列→口味」层级 | 10–13 s | **首选** |
| `glm-4v-flash` | 把分类标题当菜名 | 6–10 s | 仅作降级 |

测试样本：一张分类式比萨菜单（至尊系列 5 个口味 + 精选系列 3 个口味，价格写在系列标题行）。

- flash 输出：`至尊系列 9寸普通庄 / 至尊系列 12寸大庄 / …` —— 全错
- plus 输出：`超级至尊 / 海鲜至尊 / 香荤至尊 / 荤素满堂 / 海底金枪 / 榴莲多多 / 夏威夷风情 / 意式培根` —— 全对

**结论：视觉场景准确率优先于速度。** 识别错食材 → 健康结论错 → 产品价值归零。

**文本模型**

| 模型 | 结果 | 耗时 | 结论 |
|---|---|---|---|
| `glm-4-flash` | 指令跟随正常 | 0.8–1.1 s | **默认** |
| `glm-5.3-flash` | 更强 | ~3 s | 候选 |
| `glm-4.6-flash` | 403 | — | 本账号未开通，已从候选移除 |

### 4.2 三层降级

```
供应商层：[GLM, DeepSeek]              ← AI_PROVIDER 可强制指定
模型层：  glm-4v-plus → glm-4v-flash → glm-5.3-flash
传法层：  data:image/jpeg;base64,… → 裸 base64
```

最多尝试 8 次，全失败才报错，并在错误信息里带出**最后一次的原始错误**（如「模型不存在」「余额不足」），便于排障。

为什么要三层：智谱的模型可用性随账号套餐变化，写死一个型号会在某天整体 500。

### 4.3 Prompt 设计

**结构化输出**：system 只留一句角色定义，所有约束放在 user。

**分组结构而非平铺**：中文菜单常见「系列标题 → 多口味 + 价格」的排版。若要求平铺列表，模型会把标题当菜名。改为要求输出 `groups[].items[]`、价格挂在组上，代码里展平——准确率从 0% 提到 100%（测试样本）。

**过敏原主动推导**：模型默认只从字面找过敏原，结果全空。加入明确规则后：

```
crust / 面团 / 饼底 → 含麸质谷物
cheese / 奶酪 / 芝士 → 乳制品
shrimp / 蟹 / 龙虾 → 甲壳类
```

原则：**宁可多报不可漏报**。漏报是安全事故，多报只是体验问题。

**双语一次生成**：同一次调用同时要 `name` 与 `name_zh`、`ingredients` 与 `ingredients_zh`。发两次请求会慢一倍、贵一倍，且两套结果可能对不上。

### 4.4 模型与规则的职责边界

这是本项目最重要的设计决定：

| 环节 | 由谁负责 | 原因 |
|---|---|---|
| 看懂菜单（菜名、食材、辣度） | 大模型 | 需要视觉与常识推理 |
| 判断能不能吃 | 规则引擎（纯函数） | 需要可复现、可解释、可测试 |
| 提供依据 | 知识检索 | 需要可溯源到标准 |

**不使用大模型直接下健康结论**。原因有三：

1. 不可复现：同一道菜两次调用可能给出不同结论；
2. 不可追溯：出错时无法定位是哪一步判断错；
3. 不可测试：无法写断言。

规则引擎实测 22 毫秒返回，且每条结论都带 `reasons` 与 `citations`。

### 4.5 判定规则

优先级写死，不允许模型自由发挥：

```
过敏 > 孕期 > 慢病 > 目标
```

过敏命中一律 `forbidden`，**不允许降级**。

| 类别 | 规则来源 | 示例 |
|---|---|---|
| 过敏 | 12 类过敏原 × 食材关键词 | 含虾 → 甲壳类 |
| 孕期 | 生食、酒精、高汞鱼 | 刺身 → forbidden |
| 痛风 | 内脏、浓汤、贝蟹、啤酒 | 夫妻肺片 → caution |
| 高血压 / 肾病 | 腌、咸、腊、卤、酱 | 腊肉炒饭 → caution |
| 糖尿病 | 糖醋、拔丝、蜜汁 | 糖醋排骨 → caution |
| 减脂 | 油炸、干锅、红烧、五花肉 | 回锅肉 → caution |

**真实陷阱**：「鱼香肉丝」没有鱼。代码里做了特殊处理——只有当「鱼」的唯一证据是「鱼香」时才剔除该过敏原。

### 4.6 知识检索（RAG）

- **语料**：52 条禁忌知识，每条带 title / keywords / body / source
- **检索**：关键词匹配 + 类别加权，纯内存线性扫描
- **输出**：必须带 `source`，前端展示为「依据」

实测（成都 + 痛风）：

```
夫妻肺片  caution  常见高嘌呤与中嘌呤食物清单 · 中国食物成分表（第6版）
开水白菜  caution  嘌呤含量的三档划分 · 高尿酸血症与痛风诊疗相关指南
麻婆豆腐  safe     —
```

**质量教训**：第一版对 `safe` 的菜也附依据，出现「麻婆豆腐 → 增肌补蛋白」这种字面命中但语义无关的引用。改为只给有判定理由的菜附依据后噪音消除。

### 4.7 工具调用与 MCP

系统内工具链：`get_user_profile` → `match_restrictions` → `search_knowledge` → `explain`。

对外暴露 MCP Server（`mcp/server.mjs`），零依赖实现 JSON-RPC 2.0 over stdio，提供 5 个工具：

| 工具 | 作用 |
|---|---|
| `list_cities` | 30 城与特色菜数量 |
| `city_dishes` | 某城菜品 + 三色判定 |
| `assess_dishes` | 任意菜品判定（含依据） |
| `plan_meal` | 按人数预算配一桌 |
| `dish_detail` | 语言视角 + 复刻菜谱 |

**瘦适配器**：MCP 进程不复制业务逻辑，委托给本地 HTTP API。规则只有一份实现。

### 4.8 AI 安全与兜底

| 措施 | 实现 |
|---|---|
| 过敏硬拦截 | 命中即 forbidden，不参与配菜 |
| 低置信度提示 | `confidence < 0.5` 时提示核对食材 |
| 无依据不编造 | 检索不到时回答「不确定，建议询问店员」 |
| 可人工修正 | 识别结果允许编辑菜名与食材 |
| 免责声明 | 全站明示「不构成医疗建议」 |
| 密钥隔离 | Key 仅在服务端，前端与仓库均不可见 |

## 第五章 核心功能实现

### 5.1 拍菜单（/scan）

流程：压缩 → `POST /api/scan` → 渲染菜品卡 → `POST /api/evaluate` → 展示三色 → 写入历史。

关键实现：
- 客户端压缩到长边 1280px，手机原图 4–5 MB 降到 200 KB 以内；
- 识别结果可编辑（当前版本提供「重新拍」与详情页查看，编辑表单在 B 的下一版）；
- 识别失败时保留预览图，提示换一张。

### 5.2 健康评估（/api/evaluate）

入参 `{ dishes, profile }`，出参 `{ assessments, summary, profile }`。

```
level: 'safe' | 'caution' | 'forbidden'
reasons: string[]      // 为什么
citations: string[]    // 依据（规则 ID + 知识条目）
suggestion: string | null
```

### 5.3 地域推荐（/cities、/city/[id]）

30 城按赛区分组；进入城市即按档案评估全部菜品，**不需要拍照也不需要提问**。

这是产品最有说服力的场景：用户什么都没做，系统已经知道哪几道他不能吃。

### 5.4 配一桌（/api/plan）

1. `forbidden` 的菜直接剔除（硬约束）
2. 其余按「风险等级 → 价格」排序
3. 同一做法最多 2 道，保证多样性
4. 超预算即停，并在 `notes` 里说明

实测：成都 3 人 200 元 → 4 道 ¥189，回锅肉与开水白菜标 caution。

### 5.5 菜品详情（/dish/[id]）

两个视角：
- **语言视角**（250 条）：这是什么、怎么点、文化背景
- **复刻视角**（25 道）：备料、步骤、**过敏替代**、要点

过敏替代是 C 的内容里最有价值的部分，例如麻婆豆腐的郫县豆瓣替代方案明确区分了「麸质过敏可用」与「大豆过敏不可用」。

### 5.6 档案、收藏与历史

- 档案：`PUT /api/profile`，范围校验（年龄 1–120、身高 80–250、体重 20–300），与收藏存在同一 JSON
- 收藏：去重，上限 200
- 历史：识图与查看城市自动记录，上限 50

| 无账号体系 | 数据跟设备走，换设备看不到收藏 |
| 识图 10 秒左右 | 视觉模型较大，偶发更久 |
| 冷门菜识别弱 | 低置信度时会提示核对 |
| 不构成医疗建议 | 只做禁忌提示，不做诊断 |

### 6.5 为什么不做账号

省赛阶段评估三天工作量：账号体系会同时放大后端（session、密码哈希、找回）与前端（注册、登录、鉴权拦截）的成本，而它对评分表的贡献有限。当前 `deviceId` 方案保持了 `userId` 语义，日后替换不影响调用方。

## 第七章 创新点

### 7.1 技术创新

**① 模型与规则的职责切分**

把「看懂」交给模型，把「判断」交给规则引擎。健康结论因此可复现、可解释、可测试——这在同类作品里少见，多为「把菜单丢给大模型，让模型直接说能不能吃」。

**② 一源两入口、三视角**

拍照识别结果与地域菜库共用同一个 `Dish` 结构，因此判定逻辑只写一遍；同一份数据可以被「健康 / 语言 / 复刻」三个视角消费。

**③ 能力外溢到 MCP**

不只做界面，把能力做成 MCP 工具，任何 Agent 都能调用。这是 2026 年行业标准的用法，也是产品形态的一部分。

### 7.2 应用创新

**① 地域推荐默认带判定**

用户选一个城市，不需要拍照、不需要提问，系统已经知道哪几道他不能吃。这个交互形态在现有产品中未见。

**② 复刻视角讲「过敏怎么换料」**

不是给一份菜谱，而是给一份「你这情况怎么改」的方案，并按过敏类型分流。

## 第八章 总结与展望

### 8.1 完成情况

7 个页面、10 个接口、1 个 MCP Server、250 道菜的地域库、52 条知识、13 次提交跨 5 天完成。

### 8.2 不足

- 无账号体系，数据不跨设备；
- 识图延迟偏高，影响首次体验；
- 语言视角与复刻视角仅覆盖部分菜品（250 / 25）；
- 菜品编辑表单尚未在页面落地。

### 8.3 后续方向

1. 接入真实商家数据（菜单与价格），从「判断」走向「下单前决策」；
2. 用向量检索替换关键词检索，支持自然语言问法（「有没有不太辣、不太油的」）；
3. 支持拍照后多轮追问，如「换个便宜的方案」；
4. 账号体系与多设备同步。
