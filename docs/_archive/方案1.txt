## 二、产品定义

**名称（暂定）**：食鉴 —— 一份看得懂菜单、也看得懂你的 AI 美食助手

**一句话**：注册时填一次身体数据，之后无论拍菜单还是选城市，它都会告诉你「这道菜我能不能吃、为什么」。

**核心问题**：点评类平台解决「去哪吃」，不解决「我能不能吃」。过敏、三高、孕期、减脂人群在外就餐时缺乏可靠判断依据。

**目标用户**：有饮食限制的普通消费者（过敏人群、慢病人群、孕妇、健身减脂人群）+ 想了解地域特色菜的旅行者。

## 三、信息架构

```
登录 / 注册
   └─ 身体档案（一次性填写，可修改）
        ├─ 基础：性别 · 年龄 · 身高 · 体重 · 活动量
        ├─ 目标：减脂 / 增肌 / 控糖 / 控嘌呤 / 无特殊
        ├─ 过敏原：海鲜 / 花生 / 乳制品 / 麸质 / 蛋 / 大豆 …
        └─ 忌口：宗教戒律、素食、孕期

首页（两个入口，共用同一个「菜品对象」）
   ├─ ① 拍菜单 → 菜品理解卡 → 三个视角 Tab
   │        ├─ 健康视角：安全 / 注意 / 别点 + 原因
   │        ├─ 语言视角：这是什么菜、怎么点
   │        └─ 复刻视角：回家怎么做、缺料怎么替代
   │
   └─ ② 选地域 → 城市特色菜列表 → 每道菜直接标「适不适合你」
            └─ 选中若干道 → 生成点菜组合卡
```

**关键设计**：地域特色菜库与拍照识别结果**使用同一个数据结构**，因此健康评估逻辑只写一遍，两种入口都能用。

## 四、核心数据模型

### 4.1 菜品对象（整个项目的地基）

```json
{
  "id": "dish_sichuan_001",
  "name": "干锅花菜",
  "region": "川菜",
  "city": "成都",
  "ingredients": ["花菜", "五花肉", "干辣椒", "花椒", "豆豉"],
  "method": "干锅",
  "flavors": ["辣", "咸香"],
  "spicy_level": 2,
  "allergens": ["大豆"],
  "tags": ["高油", "高盐", "含猪肉"],
  "reference_price": 38
}
```

### 4.2 用户档案

```json
{
  "gender": "male",
  "age": 21,
  "height_cm": 175,
  "weight_kg": 78,
  "activity": "light",
  "goal": "fat_loss",
  "allergens": ["shellfish"],
  "conditions": ["hyperuricemia"],
  "dietary": ["no_alcohol"]
}
```

**派生值**：BMI、BMR（基础代谢）由前端计算并展示，不进模型上下文——模型只需要结论。

### 4.3 判定规则（健康视角的核心）

| 条件 | 规则 | 输出 |
|---|---|---|
| 过敏原命中 | 菜品 allergens ∩ 用户 allergens ≠ ∅ | **别点**（红色） |
| 慢病限制 | 痛风 → 高嘌呤；高血压 → 高盐；糖尿病 → 高糖 | 注意 / 别点 |
| 孕期 | 生食、含酒精、高汞鱼类 | 别点 |
| 目标匹配 | 减脂 → 高油高糖；增肌 → 高蛋白加分 | 提示 |
| 宗教忌口 | 含猪肉 / 含酒精 | 别点 |

> **优先级**：过敏 > 孕期 > 慢病 > 目标。过敏命中一律红色，不允许降级。

## 五、模块与工时

| 编号 | 模块 | 内容 | 依赖 | 工时 | 优先级 |
|---|---|---|---|---|---|
| M0 | 账号 + 身体档案 | 注册登录、档案表单、BMI/BMR、session | — | 1.5d | **P0** |
| M1 | 菜品理解 | 拍照 → 视觉模型 → 统一 JSON，可编辑修正 | M0 | 3d | **P0** |
| M2 | 健康视角 | 规则引擎 + 禁忌库检索 + 三色分级 | M1 + 禁忌库 | 1.5d | **P0** |
| M3 | 地域特色推荐 | 城市 → 特色菜列表 → 一键健康评估 | 地域库 | 2d | **P0** |
| M4 | 点菜组合 | 人数 + 预算 + 档案约束 → 配一桌 | M2/M3 | 1d | P1 |
| M5 | 语言视角 | 菜名解释、点菜话术、文化背景 | M1 | 0.75d | P1 |
| M6 | 复刻视角 | 家常做法 + 食材替代 | M1 + 菜谱库 | 1d | P2 |

**总工时 ≈ 10.75 天·人**，三人并行约 3.6 天/人，可行。

**并行关键**：M3（地域推荐）不依赖 M1（拍照识别），可第一周同步开工 —— 这是把关键路径压下来的关键安排。

## 六、AI 链路

### 6.1 拍照 → 理解（M1）

1. 用户上传图片（压缩到 ≤ 1600px 长边）
2. 视觉模型输出严格 JSON（给定 schema，字段缺失填 null）
3. 前端渲染为可编辑的「菜品理解卡」（允许用户改菜名、加食材）
4. 用户点「评估」→ 条件 M2

> 设计要点：**允许人工修正**。识别错一次不会毁掉体验，而且「可修正」本身就是 AI 安全可控的体现。

### 6.2 健康评估（M2）

工具链四步，模型自主决定顺序：

| 步骤 | 工具 | 说明 |
|---|---|---|
| 1 | `get_user_profile()` | 读档案（只读，不含身份信息） |
| 2 | `match_restrictions(dish)` | 规则库精确匹配 → 三色 |
| 3 | `search_knowledge(keyword)` | FTS 检索禁忌依据（如「痛风 嘌呤」） |
| 4 | `explain(dish, level)` | 生成人话解释 + 引用来源 |

**输出必须带依据**：例如「含虾皮 —— 与你的『海鲜过敏』冲突（依据：八大类过敏原清单）」。
无依据时必须说「不确定，建议询问店员」，**禁止编造**。

### 6.3 地域推荐（M3）

1. 用户选城市 → 查询地域菜品库 → 卡片列表
2. 每张卡片**默认跑一遍 M2**，直接显示「✅ 适合你 / ⚠️ 注意 / ⛔ 别点」
3. 点进详情 → 语言视角（这是什么菜）+ 复刻视角（怎么做）

> 这一步是全场最出彩的：用户不用拍照、不用提问，系统已经知道你不能吃哪道。

### 6.4 点菜组合（M4）

输入：人数、预算、口味偏好
约束：档案限制（硬约束）+ 荤素搭配 + 辣度均衡（软约束）
输出：一桌菜 + 总价 + 风险提示 + 替换建议

## 七、数据方案

### 7.1 地域特色菜库（M3 的命脉）

- 目标规模：**30 个城市 × 8–10 道 = 约 250 道**
- 来源：公开地方菜系资料 + 菜谱网站
- 构建方式：**LLM 生成初稿 → 人工校验 50 条 → 入库**。文档里如实写这个过程（这本身是 AI 工程能力的展示，不是减分项）
- 字段严格对齐 4.1 的菜品对象 schema

### 7.2 禁忌知识库

- 八大类过敏原清单（公开标准）
- 慢病饮食限制：痛风（嘌呤）、高血压（钠）、糖尿病（糖）、肾病（蛋白/钾）
- 孕期禁忌：生食、酒精、高汞鱼
- 药物-食物相互作用（头孢+酒等常见项）

### 7.3 菜谱库（M6，P2 可砍）

- 20–30 道常见家常菜的步骤与食材替代规则，不做全量

### 7.4 检索实现

**SQLite + FTS5 全文检索**，不做向量库。

> 理由：DeepSeek 不提供向量化接口，第一版引入 embedding 服务等于多养一个依赖，收益不足以覆盖 10 天的风险。文档中写明这是有意识的取舍（精确匹配场景下 FTS 召回已经够用）。

## 十一、砍功能顺序（提前定，别到第 6 天再慌）

| 卡住的情况 | 决策 |
|---|---|
| M1 识别不稳 | 支持手动输入菜名，识别仅作加速 |
| 时间不足 | **砍 M6 复刻**（P2） |
| 再不足 | **砍 M5 语言视角** |
| 极限情况 | **砍 M4 点菜组合**，保留 M0/M1/M2/M3 四个 P0 |
| 绝对不能砍 | M1 菜品理解、M2 健康视角 —— 这是产品的立身之本 |

**砍一个模块不扣创新分，交半个模块才扣。**

## 十二、风险与对策

| 风险 | 对策 |
|---|---|
| 视觉识别错菜品 → 给出错误的健康结论 | 结果卡可编辑；高亮「请确认食材」；过敏项要求用户二次确认 |
| 被质疑「健康建议」的合规性 | 全站明示「不构成医疗建议」；只做「禁忌提示」不做「诊断」 |
| 地域菜品库质量 | 只入库校验过的 250 道；标注数据来源 |
| 10 天做不完 | 严格执行第十一节的砍功能顺序 |
| 部署成本 | 国内轻量服务器 + Nginx，单机足够 |
