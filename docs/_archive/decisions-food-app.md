## 三、技术事实核查（2026-11-09 查官方文档）

- 智谱当前主推 **GLM-5.3-Flash**：原生多模态（图片/视频/文件/文本输入），上下文 1M，支持工具调用、结构化输出；价格输入 0.8 元/百万 tokens、输出 2.8 元/百万（缓存命中 0.23）。GLM-5.3-FlashX 更快（200 tok/s），2 / 7 元。
- 官方「最新模型」表里**没有免费模型**；GLM-4-Flash 等旧免费模型是否仍可调用，以控制台模型广场为准。→ 代码里模型名走环境变量，随时可换。
- 成本估算：一场比赛几千次调用，**API 花销 < 10 元**。
- 备选：DeepSeek `deepseek-flash` 也支持图像理解，输入 1–2 元/百万 tokens，可做兜底（接口同为 OpenAI 兼容格式）。
- 本机环境：Node **v22.19.0**、npm 10.9.3、Git 已装、无 pnpm（可用 corepack 或直接 npm）。

## 四、原方案里必须修的四个点

1. **MCP 名不副实**：原方案 4 个工具是 function calling，不是 MCP。补一个真 MCP server（stdio），评分项 4% 才拿得到。
2. **FTS5 中文分词是坑**：SQLite 默认 `unicode61` 把整句中文当一个 token；`trigram` 又要求查询 ≥3 字，「痛风」「嘌呤」两字查不到。→ 改用**关键词倒排表 + 同义词扩展**（数据仅 300–500 条，毫秒级），并可讲成「领域词典增强检索」。
3. **250 道菜只校验 50 条**：评委一问准确性就露。→ 全量人工过一遍（3 人分 1.5 小时）。
4. **Agent 别写成固定四步**：模型能看中间结果、失败可重试、可改调用顺序，才算 Agent；同时保留 trace 日志给评委看。

## 五、方案对比（已选 A，2026-11-09）

### 方案 A：Nuxt 3 全栈单体（Vue 生态）✅ 已选
- 技术栈：Nuxt 3 + Vue 3 + TS + Nitro server routes + SQLite（Drizzle/better-sqlite3）+ Tailwind
- 优点：单仓单进程，`npm run dev` 前后端一起起；文件路由、auto-import；端到端类型
- 风险：Nuxt 概念多（SSR/hydration 可 `ssr:false` 规避）；原生模块编译问题需 Prisma 兜底
- 选它因为：纯本地单机部署、10 天工期、三人靠 API 契约并行 —— 方案 B 的 RSC 概念成本高，方案 C 多两个进程和 CORS 联调成本，收益都不足以覆盖风险。

### 方案 B：Next.js 15 全栈（React 生态）
- 技术栈：Next App Router + Route Handlers + Prisma + SQLite + Tailwind
- 优点：React 熟队的最高效率；生态最大
- 风险：App Router / RSC / Server Actions 概念重，10 天容易绕晕

### 方案 C：Vite + Vue 3 + Fastify 前后端分离
- 技术栈：Vite + Vue 3 + TS + Fastify + Drizzle + SQLite
- 优点：架构最「教科书」，评委一眼看懂；三边界清晰好并行
- 风险：两个进程、CORS、类型两处定义、联调成本

## 六、跨方案通用技术决定（已定，不再讨论）

- 数据库：SQLite 单文件 `data/app.db`；迁移用 Drizzle 或 Prisma migrate。
- 认证：用户名 + 邮箱 + 密码（bcryptjs，纯 JS 免编译）；session 用 HMAC 签名 cookie（iron-session 或自写）。
- 检索：关键词倒排 + 同义词表 + 打分排序，**不引入向量库、不用 FTS5**。
- MCP：`@modelcontextprotocol/sdk` 写 stdio server，与 App 共用同一份规则/检索逻辑。
- 图片：前端压到长边 1600px → base64 送模型；同时落盘 `data/uploads/` 供历史记录。
- 演示：`host: 0.0.0.0`，手机同 WiFi 访问局域网 IP 拍菜单；Windows 防火墙放行端口。
