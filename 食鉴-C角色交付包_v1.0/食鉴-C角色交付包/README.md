## 二、A/B 怎么用（30 秒上手）

### A（AI/后端）

```bash
# 1. 读契约
01_数据规格/菜品对象字段规范.md      # 11 个字段、取值、校验规则
01_数据规格/vocab.json               # 唯一真源：标签/过敏原/味型/做法/城市

# 2. 读规则与知识（照 README 的伪代码接）
03_禁忌库/README.md                  # 规则 DSL、优先级、evaluate 伪代码
03_禁忌库/knowledge_entries.json     # 建 FTS5 表

# 3. 导入数据
02_地域菜库/dishes.json              # 直接 seed 进 SQLite
02_地域菜库/cities.json

# 4. 提交前自检
node 07_工具/build.mjs --check       # 全量校验，退出码 0 才许合并
node 07_工具/build.mjs --dish out.json  # 单条校验：M1 模型输出的 JSON 直接丢进来
```

### B（前端）

- 城市列表：读 `cities.json`，按 `area` 分组；`dish_count` 直接显示。
- 菜品卡：只读 11 个字段；`tags`/`allergens` 不要自己再解析一遍，等 A 的 `evaluate` 返回三色。
- 语言视角：`language_view.json` 按 `dish_id` 取三段文案（是什么 / 怎么点 / 文化）。
- 复刻视角：`recipe_view.json` 按 `dish_id` 取；`substitutions` 是核心，别只展示菜谱。
- 档案页过敏原多选：选项直接来自 `03_禁忌库/allergens.json` 的 12 个 `name`，顺序也一样，别自造文案。

### 三方共同约定

- **字段不加不改**。要改先改 `01_数据规格/菜品对象字段规范.md` 与 `vocab.json`，再由 C 回刷 250 条。
- **枚举不许自创**。模型造词 = 解析失败，前端要有降级。
- **规则是数据**。要加限制就加 JSON，不要写死 `if`。

## 四、数据是怎么来的（一句话版）

`LLM 分 6 组并行出初稿` → `规则引擎 20+ 项交叉校验`（食材推出虾皮却没标甲壳类 = error）→ `硬标签自动补全 21 条`（逐条留记录）→ `人工抽检 50 条`（20%，明细可查）→ `入库`。

证据链：`parts/`（初稿）→ `数据质量报告.json`（校验）→ `自动补全记录.md` → `人工抽检记录.md`。写技术文档时直接引用这四份，比任何形容词都有说服力。
