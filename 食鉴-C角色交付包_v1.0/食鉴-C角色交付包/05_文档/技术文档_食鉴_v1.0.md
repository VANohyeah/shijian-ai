## 1 项目概述

### 1.1 一句话

注册时填一次身体数据，之后无论拍菜单还是选城市，它都会告诉你「这道菜我能不能吃、为什么」。

### 1.2 要解决的问题

点评类平台解决的是「去哪吃」，不解决「我能不能吃」。一份菜单上，干锅花菜里的五花肉、水煮鱼里的虾皮、卤味里的料酒、凉菜里的一勺香油，对普通人只是风味，对特定人群却是风险来源：

- 食物过敏人群：中餐的酱油、蚝油、虾皮、花生油几乎无处不在，靠自己逐道询问店员，成本高且不可靠；
- 慢病人群（痛风、高血压、糖尿病、肾病）：需要判断的不只是「咸不咸」，而是嘌呤、钠、糖、钾磷的具体来源；
- 孕期人群：生食、酒精、高汞鱼是硬禁忌，但菜单上不会写；
- 健身减脂人群：需要快速判断油、糖、蛋白的比例；
- 旅行者：想了解地域特色菜「是什么、怎么点、回家怎么做」，但缺少可靠入口。

### 1.3 产品形态

两个入口，一个内核：

1. **拍菜单**：拍照 → 视觉模型输出结构化菜品对象 → 可编辑的「菜品理解卡」→ 健康评估；
2. **选地域**：选择城市 → 该城特色菜列表 → 每道菜**默认**已完成健康评估，直接显示「适合你 / 注意 / 别点」。

关键设计是**同一个菜品对象**：拍照识别结果与地域菜库使用完全相同的 11 个字段，因此健康评估逻辑只写一遍，两个入口共用。

### 1.4 与同类产品的差异

| 维度 | 点评类平台 | 通用 AI 助手 | 食鉴 |
|---|---|---|---|
| 输入 | 店、菜、评价 | 任意问题 | 菜单照片 / 城市 |
| 健康判断 | 无 | 需用户主动问，且常编造 | 默认给出，带依据 |
| 依据 | 用户评论 | 模型记忆 | 规则库 + FTS 知识库，可追溯 |
| 忌口覆盖 | 无 | 不稳定 | 过敏/孕期/慢病/宗教/目标五类硬约束 |
| 输出形态 | 列表 | 一段话 | 三视角卡片（健康/语言/复刻）|

## 2 需求分析

### 2.1 用户画像与场景

| 画像 | 典型场景 | 核心诉求 | 对产品的硬要求 |
|---|---|---|---|
| 海鲜过敏的白领 | 商务聚餐，菜单上没有配料表 | 别让我在饭桌上反复问服务员 | 过敏命中必须一眼可见，不允许「可能含」的模糊表述 |
| 痛风中年男性 | 朋友约火锅 | 哪些能吃、能喝多少汤 | 嘌呤分级准确，汤底要单独提示 |
| 孕期女性 | 旅行中想吃当地特色 | 生腌、醉蟹能不能碰 | 生食/酒精/高汞鱼必须硬拦截 |
| 减脂大学生 | 食堂与外卖 | 哪个菜热量低 | 油糖提示，不要道德说教 |
| 外地游客 | 到成都/潮州/西安 | 这菜是什么、怎么点 | 语言视角要能直接照着说 |

### 2.2 功能需求与优先级

| 编号 | 模块 | 功能 | 优先级 |
|---|---|---|---|
| M0 | 账号与档案 | 注册登录、身体档案（性别/年龄/身高/体重/活动量/目标/过敏原/慢病/忌口）、BMI/BMR | P0 |
| M1 | 菜品理解 | 拍照 → 视觉模型 → 结构化菜品对象 → 可编辑修正 | P0 |
| M2 | 健康视角 | 规则引擎 + 禁忌库检索 + 三色分级 + 依据引用 | P0 |
| M3 | 地域推荐 | 城市 → 特色菜列表 → 默认健康评估 | P0 |
| M4 | 点菜组合 | 人数 + 预算 + 档案约束 → 一桌菜 + 风险提示 + 替换建议 | P1 |
| M5 | 语言视角 | 菜名解释、点菜话术、文化背景 | P1 |
| M6 | 复刻视角 | 家常做法 + 食材替代（含过敏替代） | P2 |

### 2.3 非功能需求

| 类别 | 要求 | 落地方式 |
|---|---|---|
| 性能 | 菜单识别 ≤8s，健康评估 ≤3s | 图片压到长边 1600px；评估走规则引擎，不重复调用大模型 |
| 可用性 | 模型超时要有兜底 | 降级为手动输入菜名 + 规则库评估，功能不中断 |
| 安全 | 过敏命中不可被模型降级 | 规则引擎前置，模型只负责解释，不负责定级 |
| 合规 | 全站明示「不构成医疗建议」 | 固定页脚 + 每张卡片底部 |
| 隐私 | 身体数据与用药信息不外泄 | 派生值（BMI/BMR）前端算；用药只做服务端一次性匹配，不入日志 |
| 移动端 | 单手可操作 | 卡片式布局，主按钮固定底部 |

### 2.4 关键取舍

1. **不用向量库，用 SQLite FTS5**：DeepSeek 不提供向量化接口，第一版引入 embedding 服务等于多养一个依赖。禁忌知识条目是短文本、关键词高度集中（「痛风」「嘌呤」「虾皮」），精确检索的召回已经够用。这是有意识的取舍，不是能力缺失。
2. **模型不做定级，只做解释**：三色分级由规则引擎算出，模型只把结论翻译成人话。这样同一道菜同一份档案，结论永远一致，也不会出现「模型心情好就说能吃」。
3. **允许人工修正识别结果**：识别错一次不毁体验；「可修正」本身就是 AI 安全可控的体现。
4. **地域库不做全量**：只做 30 城 250 道，且只入库校验过的数据。宁可少，不可错——这是健康类产品与内容类产品的根本区别。

### 3.3 核心数据结构

菜品对象是整个项目的地基，11 个字段，拍照识别与地域库共用：

```json
{
  "id": "dish_chengdu_01",
  "name": "麻婆豆腐",
  "region": "川菜",
  "city": "成都",
  "ingredients": ["豆腐", "牛肉末", "郫县豆瓣", "花椒面", "蒜苗", "豆豉"],
  "method": "烩",
  "flavors": ["辣", "麻", "咸鲜"],
  "spicy_level": 3,
  "allergens": ["含麸质谷物", "大豆"],
  "tags": ["高油", "高盐", "含牛肉", "中嘌呤"],
  "reference_price": 28
}
```

> 上面这条就是仓库里 `dish_chengdu_01` 的真实记录，可直接复制去跑校验：`node 07_工具/build.mjs --dish dish.json`。
> `method` 是**单个字符串**而不是数组：受控词表里已经用「酥炸」「干锅」「粉蒸」这类复合值表达工艺组合，一道菜只记「上桌形态对应的主工序」。若改成数组，M1 的 prompt、前端渲染、250 条历史数据都要同步改，收益不抵成本——这是明确的设计决定，不是遗漏。

- `tags` 是规则引擎唯一读取的字段，共 33 个，分风险/荤腥/安全/形态四组；
- `allergens` 是过敏硬拦截的输入，12 个大类，前 8 类对齐 GB 7718-2011；
- 溯源信息（生成方式、校验结果、抽检记录）不进主对象，单独放 `dish_source.json`。

### 3.4 数据流

```
拍照 ──→ 压缩 ──→ 视觉模型 ──→ 菜品对象(JSON) ──→ 用户可编辑修正
                                                    │
选城市 ──→ dish 表 ─────────────────────────────────┘

```

## 4 AI 技术方案

### 4.1 视觉理解与结构化输出（M1）

Prompt 由四部分组成：角色设定、字段契约、判定口径、两个 few-shot（一个普通菜、一个高风险菜）。

设计要求：
1. **严格 JSON**：给定 11 个字段与枚举取值，字段缺失填 `null`，不允许自创字段；
2. **只写看得见的**：菜单上没有的配料不猜；看不出来的价格返回 `null`；
3. **枚举受控**：`tags`/`allergens`/`flavors`/`method` 的取值来自受控词表，模型不许造词——造词直接判为解析失败并降级；
4. **可修正**：识别结果渲染为可编辑卡片，用户能改菜名、增删食材，改完重新推导过敏原（用食材映射表，不重跑模型）。

容错：
- JSON 解析失败 → 重试 1 次（附错误信息）→ 仍失败则降级到手动输入；
- 置信度低（菜品名不在菜名库且配料少于 3 项）→ 卡片顶部提示「识别可能在以下方面不准确，请确认食材」。

### 4.2 Agent 四步工具链（M2）

| 步骤 | 工具 | 职责 | 是否调模型 |
|---|---|---|---|
| 1 | `get_user_profile()` | 读档案，只读，不含身份信息 | 否 |
| 2 | `match_restrictions(dish)` | 规则精确匹配 → 三色 + 命中规则 + 依据 id | 否 |
| 3 | `search_knowledge(keyword)` | FTS5 检索禁忌依据 | 否 |
| 4 | `explain(dish, level)` | 生成人话解释 + 引用来源 | 是 |

要点：
- 模型**不决定**三色，只决定「怎么解释」。这样评估结果可复现、可审计，不会因模型采样而变化；
- 模型的自主性体现在**编排**：它可以决定是否为某道菜额外检索（例如「这道菜名陌生，先查一下是什么」），也可以决定解释的详略；
- 四个工具都是纯读操作，不产生副作用，符合 Agent 工具设计的基本安全原则。

### 4.3 RAG：为什么是 FTS5

| 方案 | 优点 | 缺点 | 本项目结论 |
|---|---|---|---|
| 向量库（embedding） | 语义泛化好 | 需额外模型与向量存储；DeepSeek 无向量接口；口语短句上收益有限 | 不采用 |
| SQLite FTS5 | 零依赖、中文关键词命中准、可解释 | 不懂同义词 | **采用**，用 `keywords` 字段人工补同义词 |
| 纯 LIKE | 最简单 | 无排序、慢 | 仅作兜底 |

知识条目共 52 条，每条含 `id / title / keywords / category / body / source / confidence`。`keywords` 里刻意塞满口语说法（「尿酸高」「痛风」「嘌呤」「海鲜能不能吃」），弥补 FTS 不懂同义词的短板。

检索策略：先用规则命中的 `evidence` id 精确取条目（保证解释与规则同源），再用用户问题关键词做 FTS 补充检索；两路结果按 `confidence` 排序，最多取 3 条注入 prompt。

**已知边界（写清楚，别让评委替我们发现）**：FTS5 没有语义泛化能力，召回完全取决于 `keywords` 里有没有写对词。例如用户问「尿酸高能吃海鲜吗」，如果条目关键词里没有「尿酸高」「海鲜」，就会漏检。本项目的应对是：① 规则命中时直接按 `evidence` 取条目，不依赖检索；② `keywords` 人工补齐口语说法与同义词；③ 检索为空时走固定兜底话术。**下一步**（v1.1 可选）会补一组 20 条 query 的检索评测，把召回率写进文档，而不是只说「够用」。

### 4.4 规则引擎：可解释与可复现的来源

规则用声明式 JSON 描述，不写死在代码里：

```json
{
  "id": "gout_forbid_organ",
  "match": { "tags_all": ["含内脏"] },
  "level": "forbid",
  "message": "{name} 含动物内脏（命中：{ingredients}），嘌呤含量在常见食物中最高一档，建议不要点。",
  "evidence": ["kb_purine_02"]
}
```

- `match` 内各字段之间是 AND，数组内部是 OR。**所以「标签 A 或 食材 B」必须拆成两条规则**——写成一条会变成 A 且 B，几乎永远不命中（`conditions.json` 里痛风的嘌呤规则就是因此拆成了 `gout_forbid_purine_tag` 与 `gout_forbid_purine_food` 两条）；
- 多条规则命中取最高等级（forbid > caution > info > ok）；
- 优先级：**过敏 > 孕期 > 忌口/宗教 > 慢病 > 目标**。过敏命中一律红色，任何情况下不允许降级；
- **药物-食物相互作用不参与三色定级**：它只对「正在服药」的用户生效，是一个临时状态，不能因为一道菜把没吃药的用户标红。因此 `drug_food.json` 的 level 只表示提示强度，渲染时走卡片底部的独立提示条，不并入 `max_level`。

这样做的好处：新增一条限制只改 JSON，不动代码；每条结论都能追到规则 id 与知识条目 id，写文档和答辩时可以直接摊开给人看。

### 4.5 AI 安全设计

| 风险 | 设计 |
|---|---|
| 模型把过敏菜说成「可以吃」 | 三色由规则引擎定，模型无权限修改；输出前做一致性校验，模型文本与规则结论矛盾则丢弃重写 |
| 模型编造配料/营养数据 | 无依据时固定话术：「配料无法从图片确认，建议询问店员：是否含××」；禁止输出未在 dish 对象中的食材 |
| 识别错菜 | 结果卡可编辑；过敏项要求二次确认；高风险菜顶部提示请核对食材 |
| 健康建议越界 | 全站「不构成医疗建议」；只做禁忌提示，不做诊断与治疗建议 |
| 数据不可信 | 250 道全部经规则校验，50 道人工抽检；文档如实记录 LLM 初稿 + 人工校验的过程 |

### 4.6 多模态与工具化

- **多模态**：菜单照片 → 结构化菜品对象，是典型的「图 → 结构」任务，评分点在于 schema 约束与容错，而不是识别本身；
- **工具化**：四个自定义工具（档案、规则、检索、解释）边界清晰，可被未来接入 MCP 复用；
- 工具返回结构化结果而非自然语言，模型只做最后一步「翻译」。

### 5.2 地域菜库如何构建

**规模**：30 城 × 8–9 道 = 250 道。城市覆盖七大区：华北 3、东北 2、华东 9、华中 3、华南 5、西南 5、西北 3。

**流程（四步，可复现）**：

1. **LLM 分城市生成初稿**：按大区分 6 组并行，每组 5 城。提示词固定字段契约、受控词表与打标口径，要求只写真实存在、当地人公认的特色菜，跨城不重名。
2. **规则引擎交叉校验**：`build.mjs` 对每条记录做 20 余项检查（见 5.5），重点是「食材 → 过敏原/标签」的自洽性：写了虾皮却没标甲壳类，直接判 error。
3. **硬标签自动补全**：食材映射表能确定的事实（过敏原、猪牛羊禽内脏海鲜蛋乳酒精生食）缺标时自动补齐，并输出 `自动补全记录.md`；风险类标签（高油/高盐）不自动补，避免机器替人判断口味。
4. **人工抽检 50 条**：按固定步长抽样，逐条核对菜名真实性、菜系归属、配料合理性、过敏原标注，记录问题与修复。

**为什么敢说数据是真的**：每一步都有产物——初稿在 `parts/`，校验结果在 `06_验收/数据质量报告.json`，补全记录在 `06_验收/自动补全记录.md`，抽检记录在 `06_验收/人工抽检记录.md`。这不是「我们收集了 250 道菜」，而是「我们这样生产并验证了 250 道菜」。

### 5.3 禁忌知识库怎么设计

五类规则 + 一份知识库：

| 类型 | 触发条件来源 | 典型规则 | 等级 |
|---|---|---|---|
| 过敏 | `allergens` ∩ 用户过敏原 | 命中即红 | forbid |
| 孕期 | 生食/半生食/酒精/高汞鱼 | 生腌、醉虾、溏心蛋 | forbid |
| 忌口/宗教 | 猪肉、酒精、动物性调味 | 清真、全素、忌酒 | forbid |
| 慢病 | 高嘌呤/高盐/高糖/高钾磷 | 内脏、腌腊、甜汤 | caution/forbid |
| 目标 | 高油/高糖/精制碳水/高蛋白 | 减脂、增肌、控糖 | info/caution |

设计原则：
- **硬约束不允许降级**。过敏、孕期、宗教戒律命中即红，不提供「少量食用」选项；
- **软约束只做提示**。减脂期看到红烧肉提示「可两人分食」，而不是禁止；
- **每条规则带 `evidence`**，指向知识库条目，解释生成时强制引用；
- **规则与知识分离**：规则决定「是什么等级」，知识决定「为什么」。

### 5.4 数据契约：三端并行的前提

A 写模型 prompt、B 写卡片、C 写数据，三方最容易在字段上打架。解决办法是先定契约：

- `01_数据规格/菜品对象字段规范.md` 定 11 个字段、取值、校验规则；
- `01_数据规格/vocab.json` 是**唯一真源**，标签、过敏原、味型、做法、城市都从这里取；
- 校验脚本是契约的执行者，谁改字段谁跑脚本，CI 里退出码非 0 就不许合并。

这套做法让三个人可以并行十天而不互相等待——这也是 10 天三人做完一个完整作品的真正原因。

### 5.5 质量度量

最近一次全量校验结果：

| 指标 | 数值 | 说明 |
|---|---|---|
| 菜品 | 250 | 30 城全部达标，无缺城 |
| 语言视角 | 250 | 与菜品一一对应，无孤儿条目 |
| error | **0** | 字段、枚举、id、过敏原自洽全部通过 |
| warn | 35 | 主要是「食材可推出腌制/加工肉标签但未标」的风险标签建议，不影响三色判定 |
| info | 289 | 映射表未收录的食材名（如「黄喉」「脆哨」），已记录，作为词表覆盖度的刻度 |
| 规则 | 46 条 + 11 条药物相互作用 | 引用知识条目 52 个 id，全部存在（无断链） |
| 自动补全 | 21 条 | 每条都有记录可查 |
| 人工抽检 | 50 条（20%） | 逐条回填到 `dish_source.json` 的 `human_reviewed` 字段，可机器核验 |

> **`error = 0` 的边界要说清**：它只代表**语法、字段、枚举与引用完整性**通过，不等于业务逻辑零缺陷。业务层面的已知问题——例如复刻菜谱里个别替代方案仍偏保守、部分菜品缺少「腌制」这类风险标签——属于业务判断，记录在 `06_验收/已知缺陷清单.md`，用 warn 而不是 error 表达。技术上把它们混进 error 会让校验失去区分度，反而掩盖真正的数据错误。这一点在答辩时也照实说。

warn 与 info 不清理的理由：warn 是「可以更准」而非「错了」，硬改反而会引入主观判断；info 是词表覆盖度的诚实刻度，写进文档比藏起来更有说服力。

### 5.6 数据局限（如实声明）

1. 价格是常见堂食价，不同城市、不同档次餐馆差异大，只作参考；
2. 复合调味料（火锅底料、卤料包）成分不可见，只能提示「可能含多种致敏物质」；
3. 菜品的地域归属存在争议（如锅包肉在哈尔滨与沈阳都有做法），本库按「最具代表性城市」单一归属，不做多归属；
4. 250 道覆盖的是「特色菜」，不是全菜单；用户拍到的菜大概率不在库里，此时走 M1 模型识别，不查库；
5. 营养数值（热量、嘌呤毫克数）不做精确计算，只做「高/中/低」分级——外食场景下精确数值是伪精确；
6. **复刻视角（M6）的替代方案由人工编写，不是经过验证的配方**：它解决的是「缺料/过敏时怎么换」，个别替代会改变风味甚至口感（如用辣椒酱代替豆瓣酱），文案里已标注，但不能当作过敏人群的绝对安全指引——真正的安全边界仍然由 `allergens` 与规则决定；
7. 菜品标签（尤其「高油」这类）含主观判断，不同人打标结果可能不同，因此校验只对可推导的事实强制 error。

### 6.2 规则引擎伪代码

```
function evaluate(dish, profile):
    // 第一道防线：过敏命中直接返回，不进入后续任何计算
    allergy = [a for a in profile.allergens if a in dish.allergens]
    if allergy is not empty:
        return {
            level: "forbid",
            hits:  [{ level: "forbid", rule: "allergy_" + a } for a in allergy],
            evidence: ["kb_allergen_01"]
        }

    // 第二道防线：孕期 / 忌口 / 慢病 / 目标，取最高等级
    hits = []
    if profile.pregnancy:  hits += [r for r in pregnancy.rules if match(r, dish)]
    for d in profile.dietary:   hits += [r for r in dietary[d].rules if match(r, dish)]
    for c in profile.conditions: hits += [r for r in conditions[c].rules if match(r, dish)]
    for g in [profile.goal]:    hits += [r for r in goals[g].rules if match(r, dish)]

    level = max_level(hits)      # forbid > caution > info > ok
    return { level, hits, evidence: unique(hits.evidence) }
```

要点：过敏是**早返回**，它的结论根本不进入 `max_level`，因此不存在「被后续规则覆盖」的可能。这行代码与上一段的文字描述必须一致——文档里怎么写，实现就怎么来。

## 8 创新点

### 8.1 一源三视角

同一个菜品对象，从健康、语言、复刻三个角度给出答案。这不是三个功能拼在一起，而是**一次数据结构设计带来的复用**：所有视角读的是同一份 11 字段数据，所以新增视角的成本极低，结论也永远自洽。

### 8.2 地域推荐默认带健康标记

用户不用拍照、不用提问，打开某城页面，系统已经知道哪道菜他不能吃。这是全场最出彩的一步——它把「健康助手」从被动问答变成了主动预防。

### 8.3 规则引擎与模型分工

健康结论由规则引擎给出，模型只负责解释。这条边界有两个好处：
- **可信**：结论可复现、可审计，不会今天说能吃明天说不能；
- **可答**：每条结论都能摊开成「命中哪条规则、依据哪条知识」，评委问「凭什么」时答得出来。

### 8.4 数据契约驱动三端并行

十天内三个人做出完整作品，靠的不是加班，是先用一份字段规范与受控词表把并行接口定死，再用校验脚本把契约变成可执行的约束。

### 8.5 医疗数据的克制

用药信息只做服务端一次性匹配，不入日志、不进模型上下文；BMI/BMR 前端计算，不传后端。健康类产品最容易犯的错是「多收一点数据反正有用」，本作品选择反着做。

具体机制：用户可选填当前用药 → 服务端用 `03_禁忌库/drug_food.json` 的 11 对规则做一次内存匹配 → 只返回命中的提示文案与菜名 → 匹配完立即丢弃用药信息，不落库、不写日志、不进 prompt。这既是隐私设计，也避免把「药物交互」误当成菜品本身的健康等级（见 4.4 最后一条）。

## 9 社会价值与合规

### 9.1 社会价值

- 中国食物过敏人群规模不小，但外食场景几乎没有可靠工具，本作品将「问店员」的不确定性降到最低；
- 慢病管理最难的是外食，规则化提示能真实降低风险；
- 地域菜库同时承担饮食文化科普功能，「语言视角」让外地人敢点、会点。

### 9.2 合规边界

| 事项 | 做法 |
|---|---|
| 医疗建议 | 全站明示「不构成医疗建议」，只做禁忌提示 |
| 诊断治疗 | 不做，不推荐药物，不给剂量 |
| 数据隐私 | 最小必要收集；身体数据仅用于规则匹配 |
| 用户修正 | 识别结果可改，健康结论随数据实时重算 |
| 免责 | 每张卡片底部固定一行 |

### 9.3 风险与对策

| 风险 | 对策 |
|---|---|
| 识别错菜导致错误结论 | 可编辑卡片 + 过敏二次确认 + 高风险提示 |
| 被质疑数据来源 | 溯源文件 + 抽检记录 + 文档如实披露 LLM 初稿过程 |
| 模型成本 | 规则前置，模型只解释；每日限额 |
| 评审期服务不可用 | 单机部署 + 每日备份 + 降级模式 |

| M5 语言视角 | `build.mjs` 的 `language_view` 覆盖率检查会报 error，需加 `--no-lv` 开关或在 `build.mjs` 里注释掉该段 |
| M3 地域推荐（极限情况） | `dishes.json` 不再是必需项，但 `build.mjs` 的城市数量检查会失败，需整体跳过数据构建，只保留规则单测 |
