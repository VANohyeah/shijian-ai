# 地域菜库构建与校验流程

> 这份文件回答一个问题：**250 条数据是怎么保证不出错的？**
> 赛项要求"作品须原创、保留真实开发过程"。数据同样如此——不是"我们收集了 250 道菜"，而是"我们按这个流程生产并验证了 250 道菜"。

---

## 一、目标

| 项 | 指标 |
|---|---|
| 规模 | 30 城 × 8–9 道 ≈ 250 道 |
| 城市覆盖 | 七大区：华北 3 / 东北 2 / 华东 9 / 华中 3 / 华南 5 / 西南 5 / 西北 3 |
| 字段 | 11 个，严格对齐 `菜品对象字段规范.md` |
| 质量 | 校验 error = 0；人工抽检 20%，0 条需返工 |
| 可追溯 | 每条都能查到：谁生成、过了哪些校验、补了什么、谁抽检 |

---

## 二、五步流程

```
① 词表先行  →  ② LLM 分城市初稿  →  ③ 规则交叉校验  →  ④ 自动补全  →  ⑤ 人工抽检
   （1 天）        （1 天）              （脚本，秒级）      （脚本，秒级）    （抽样 50 条）
```

### ① 词表先行（约 1 天）

在写第一条数据之前，先把"允许说什么"定死：

- `vocab.json`：30 个城市（含省份/大区/菜系/辣度基线）、33 个标签（分四组并逐个写定义）、12 类过敏原（前 8 类对齐 GB 7718）、18 个味型、30 种做法、辣度 0–5 的体感定义；
- `菜品对象字段规范.md`：11 个字段、类型、取值范围、校验规则、两个正例（一个普通菜、一个高风险菜）。

**为什么先做这一步**：如果先写数据再定词表，250 条里会出现几百种写法（"微辣/小辣/一点点辣"），后面再统一就是灾难。

### ② LLM 分城市初稿（约 1 天）

按大区分 **6 组并行**，每组 5 城，每组产出一个 `parts/gN.json`：

| 组 | 城市 | 条数 |
|---|---|---|
| g1 西南 | 成都 9 / 重庆 9 / 贵阳 8 / 昆明 8 / 拉萨 8 | 42 |
| g2 华南 | 广州 9 / 佛山 8 / 潮州 9 / 桂林 8 / 海口 8 | 42 |
| g3 华中+华北 | 武汉 8 / 长沙 9 / 郑州 8 / 太原 8 / 北京 9 | 42 |
| g4 华东 A | 上海 9 / 南京 8 / 苏州 8 / 扬州 9 / 杭州 8 | 42 |
| g5 华东 B | 宁波 8 / 福州 8 / 厦门 8 / 青岛 8 / 天津 8 | 40 |
| g6 西北+东北 | 西安 9 / 兰州 8 / 乌鲁木齐 8 / 哈尔滨 9 / 沈阳 8 | 42 |

每组提示词固定四件事：字段契约、受控词表、打标口径（食材→标签的硬规则）、自检要求（写完自己解析一遍）。
要求：只写真实存在、当地人公认的特色菜；跨城不重名；每城覆盖凉菜/汤羹/主食或小吃/招牌热菜。

**保留初稿不删**：`parts/` 原样存档，是"数据是生产出来的"最直接的证据。

### ③ 规则交叉校验（脚本，秒级）

`build.mjs` 对每条记录做 20 余项检查，分三级：

| 级别 | 检查项 | 处理 |
|---|---|---|
| error | 11 字段齐全、类型正确、id 格式与唯一性、菜名唯一、city/region 与词表一致、枚举越界、ingredients <4、tags <3、辣度/价格越界、**食材推出的过敏原/荤腥标签缺失**、语言视角缺失或孤儿 | 阻断入库 |
| warn | tags >7、flavors 越界、辣度与口味矛盾、同城价格离群（±2.5σ）、风险类标签缺失 | 记录，人工判断 |
| info | 食材映射表未收录的词、菜名与配料无字面交集 | 记录，作为词表覆盖度的刻度 |

关键设计：**只有"可推导的事实"才判 error**。虾皮 → 甲壳类是事实，缺了就是错；"这道菜算不算高油"是判断，缺了只 warn。这条边界保住了数据的客观性，也避免了机器替人下主观结论。

### ④ 自动补全（脚本，秒级）

对 error 里的"过敏原/关键荤腥标签缺失"，用食材映射表自动补齐，并逐条写入 `06_验收/自动补全记录.md`。

- 补的只有事实：过敏原、猪/牛/羊/禽/内脏/海鲜/蛋/乳/酒精/生食/高汞鱼；
- **不补**风险标签（高油/高盐/高糖/高蛋白），因为那需要整道菜的判断；
- 每次补全都留痕，谁都能查"这条数据被动过哪里"。

### ⑤ 人工抽检（20%，50 条）

按 id 排序后每 5 条取 1 条，逐条核对四件事：菜名真实性、城市/菜系归属、配料通行度、过敏原与标签自洽。结果写进 `06_验收/人工抽检记录.md`。

抽检不是形式：本次抽检发现了 1 条非关键标签缺失、2 条已知局限，并把 3 个"菜名陷阱"（荞面灌肠、鱼香、夫妻肺片）作为正面案例记录下来。

## 三、常见错误类型（真实出现过，已解决）

| 类型 | 实例 | 处理 |
|---|---|---|
| 过敏原近义写法 | 子任务写"贝类"，词表里是"贝类/软体" | 构建时做别名归一（`ALLERGEN_ALIASES`），并在词表里注明 |
| 字面误伤 | "啤酒花"被判成含酒精；"牛油"被判成乳制品；"绿豆芽"被判成大豆 | 修映射表 + 增加 `term_exclusions`（食材级例外） |
| 菜名陷阱 | 鱼香肉丝没有鱼、荞面灌肠没有肠、夫妻肺片不是肺 | 不做菜名匹配，只按 `ingredients` 匹配；`name_exceptions` 记录在案 |
| 隐藏配料漏标 | 蚝油（贝类）、虾油（甲壳类）、火腿（猪肉）、熟猪油（猪肉）、花茶（咖啡因） | 映射表收录，校验强制 error |
| 枚举疲劳 | 子任务把 method 写成"冻"（词表没有） | 校验直接报错；已知局限记录在案（马迭尔冰棍只能写"煮"） |
| 标签超限 | 复杂菜 7 个标签（毛血旺：猪+禽+牛+内脏+加工肉+高油+高嘌呤） | 把上限从 6 调到 7，因为"装不下事实"比"守规矩"更重要 |

## 四、复现方式

```bash
# 全量构建（读 parts，写 dishes/cities/language_view/质量报告）
node 07_工具/build.mjs

# 只校验已构建产物（CI 用，error 即退出码 1）
node 07_工具/build.mjs --check

# 刷新城市统计
node 07_工具/gen_city_report.mjs
```

无第三方依赖，Node 18+ 即可。数据、规则、脚本全部在仓库里，任何人 clone 下来都能复现同一次校验结果。

## 五、已知不足（写在文档里，不藏着）

1. **抽样而非全检**：50/250，剩下 200 条仍可能有同类小瑕疵；
2. **单人复核**：抽检由同一名数据负责人完成，缺交叉复核；
3. **无真实点单核对**：配料依据是通行做法，不是某家店的实际配方；
4. **价格无来源**：是常见堂食价的估计，未做多店采样；
5. **地域归属有争议**：锅包肉、狮子头这类多城共有菜，按"最具代表性城市"单一归属。

这五条都写进了技术文档 5.6 节。承认局限比假装完美更能建立可信度。
